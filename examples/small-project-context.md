##### 用户场景与测试 *(必填)*

###### 用户故事 1 - 添加一条待办（优先级：P1）

用户从终端输入文本并得到可读的新增结果。

**为何此优先级**：这是唯一的范围内旅程。

**独立测试**：在临时数据文件上运行 `todo add "买牛奶"`，随后查询列表。

**验收场景**：

1. **给定** 列表为空，**当** 运行 `todo add "买牛奶"`，**则** JSON 中新增一条未完成记录，列表显示该文本。
2. **给定** 列表已有一条记录，**当** 再运行 `todo add "缴电费"`，**则** 新记录排在既有记录之后。

###### 边界情况

- 文本为空时返回参数错误，不写入文件。
- JSON 写入失败时返回错误，不能宣称新增成功。

- **REQ-002**：系统必须按命令调用顺序保存待办。来源：NEED-001。

- **Todo**：文本、完成状态和既有仓储定义的顺序；不在本次重定义持久化格式。

### 工程上下文：FEAT-EXAMPLE-CLI 添加待办

#### 当前有效方案

##### 架构设计

**关联产品上下文**：`.sdlc-v1/context/REQ-EXAMPLE-CLI.product.md`

**工程上下文**：`.sdlc-v1/context/FEAT-EXAMPLE-CLI.engineering.md`

**状态**：Draft

###### 背景

在现有命令解析与 JSON 仓储上增加一个最小写入路径；不改变既有数据模型或远程接口。

###### 架构与组件

- **`add` 命令职责**：校验非空文本，调用仓储追加记录，打印结果。**接口**：`add <text>` → 成功文本或参数/写入错误。**覆盖**：REQ-001、REQ-002。
- **现有 JSON 仓储职责**：原子地保留既有顺序并报告写入失败。**覆盖**：REQ-001、REQ-002。

###### 关键设计决定

- **背景**：首版只需延续既有本地行为。**决定**：复用 JSON 仓储。**替代项**：新增数据库或同步服务。**取舍**：不支持跨设备。**覆盖**：CON-001、OUT-001。

###### 数据模型 / 关键实体 *(Feature 涉及数据时包含)*

- 沿用既有 `Todo` 序列；本次不新增字段、迁移或兼容性版本。

###### API / 接口契约 *(Feature 暴露 CLI 表面时包含)*

- `todo add <text>`：空文本返回非零错误且不写文件；成功时返回新增记录的可读摘要。

###### 时序与数据流 *(适用性说明)*

- 线性 CLI → 参数校验 → 仓储写入 → 输出；没有异步、重试或并发协议需要图示。

###### 横切质量设计 *(适用性说明)*

- 失败不产生部分成功输出；其余性能、安全和可用性要求沿用现有 CLI，不在本次扩展。

###### 风险与取舍 *(Feature 存在实质风险时包含)*

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 写入失败 | 用户误以为已保存 | 传播错误且以临时文件场景验证 |

| 规格需求 | 设计覆盖 |
|---|---|
| REQ-001 | `add` 参数校验和错误契约 |
| REQ-002 | JSON 仓储追加和顺序检查 |

##### 实施计划

**关联设计**：本上下文的“架构设计”

**已确认需求**：REQ-001、REQ-002

**状态**：Draft

###### 背景

先形成可从临时 JSON 调用和检查的单一旅程，再运行现有测试入口。

###### 目标 / 非目标

- **目标**：实现 `add`、空文本拒绝和追加顺序验证。
- **非目标**：JSON 格式迁移、同步、分类、UI 和无关重构。

###### 技术栈

- 沿用仓库现有 CLI 语言、测试框架和 JSON 仓储；不新增依赖。

###### 实施层决定

- **选择**：一个纵向 Task 同时改命令和紧密关联的仓储调用。**理由**：结果可以在同一 CLI 场景中验证。**覆盖**：REQ-001、REQ-002。

| 风险 | 可能性 | 影响 | 缓解措施 |
|---|---|---|---|
| 现有仓储不保序 | 低 | 中 | 先用临时文件验证；不符则回计划更新设计 |

###### 实施阶段

- **阶段 1：准备**：确认现有命令/仓储入口和测试命令；无新共享基础设施。
- **阶段 2：核心实现**：完成计划 Task `add`；**最早可检验结果**：在临时 JSON 上完整运行，新增后重新列出。
- **阶段 3：测试**：运行空文本和顺序追加的现有或新增测试。
- **阶段 4：文档与收尾**：更新受影响 usage 说明（如存在）并执行必要检查。

## 有实质 UI 选择：提问、候选和反馈

用户要做待办 UI，但没有说明首版如何组织内容。产品 Agent 先复用已有信息，只把会改变导航、规则和验收的选择交给主 Agent：

> 首版按顺序显示待办，还是按项目分类？我建议先按顺序显示：可以更快让“添加 → 完成 → 筛选”成为完整旅程；项目分类还需要导航、编辑和迁移规则。这个选择影响候选原型和 REQ-010 的验收场景。

主 Agent 用已有原生交互询问。若用户没有回答，项目分类保持 `OPEN-010`，只继续不依赖它的布局或调研；不得把推荐写成 `confirmed`，也不得推进依赖分类的验收。

如果用户回答“首版这些组织方式按你的推荐”，产品上下文可记录：

#### DEC-010: 首版采用顺序清单

- **状态**：confirmed
- **决定**：按加入顺序显示待办，不提供项目分类。
- **用户证据**：用户明确委托“这些组织方式按你的推荐”；实际采用“顺序清单”。
- **范围影响**：项目导航与编辑规则仍在范围外。

这记录的是委托和实际采用项，不能改写成“用户亲自选择了顺序清单”。“继续执行”或“全程推进”本身也不能生成这一条。

适用原型策略时，产品/规格阶段可以展示候选，而不把它当成生产通过：

> 候选原型 v0.1：打开 `prototype/index.html`，尝试“添加一条待办 → 标为完成 → 用状态筛选”。本次检查只覆盖本地模拟数据和该旅程；没有服务端持久化、权限或同步。请在完成后返回列表，确认筛选结果是否符合预期；若不是，请指出“完成后留在当前筛选”或“回到全部”。
