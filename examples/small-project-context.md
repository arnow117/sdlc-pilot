##### 需求 *(必填)*

###### 功能需求

**命令接口（唯一权威定义）**：可执行文件为 `python3 todo.py --data PATH <subcommand>`，`--data` 必填。

| 子命令 | 语义与成功输出 | 错误行为 |
|---|---|---|
| `add TEXT` | 追加 `open` 项，分配下个正整数 ID，输出 `ID open TEXT` | 空白或非严格 UTF-8 文本失败且不写入 |
| `list [--status all\|open\|done]` | 按顺序显示，缺省 `all` | 非法状态失败且不写入 |
| `complete ID` | 把现有 `open` 项改为 `done`，输出 `ID done TEXT`；已 `done` 项重复成功且不重写数据文件 | 非正或缺失 ID 失败且不写入 |
| `export --output PATH` | 按顺序写 `# Todos` 和 `- [ ]`/`- [x]` 项 | 无效/等同数据文件的目标或写入失败不破坏原文件 |

**JSON schema（唯一权威定义）**：数据文件是 UTF-8 `{"version":1,"todos":[...]}`；每项恰有唯一正整数 `id`、非空且无孤立 surrogate 的 `text`、`open`/`done` 的 `status`，数组顺序用于列表/导出。读取验证顶层、字段、类型和值；解码错误（含过深或递归）无效。写入 UTF-8、`ensure_ascii=False`、尾随换行。

**文件保护规则（唯一权威定义）**：父目录存在而数据文件缺失时视为空；`list`/`export` 不创建，只有成功 `add` 创建。有效已有数据即使父目录不可写也可读取；无效数据报错、字节不变。写操作才要求可写父目录，且不创建父目录。写前验证；导出拒绝与数据文件规范化路径相同或 symlink 别名，路径均存在时以 `samefile` 再拒绝 hardlink 身份相同。目录目标、父目录缺失/不可写或这些别名均拒绝，保留数据文件与已有输出字节。写入同目录临时文件、flush/close 后 `os.replace`；读取、校验、写入或替换失败均非零、保留原字节并清理本次临时文件；不承诺崩溃/断电耐久性。

### 工程上下文：FEAT-EXAMPLE-CLI 本地待办 CLI

#### 当前有效方案

##### 架构设计

**关联产品上下文**：`.sdlc-v1/context/REQ-EXAMPLE-CLI.product.md`

**工程上下文**：`.sdlc-v1/context/FEAT-EXAMPLE-CLI.engineering.md`

**已确认需求**：NEED-001、CON-001、OUT-001；规格的 AC-001–AC-004

**状态**：Draft（示例，NOT_RUN）

###### 背景

从空仓库交付一个可独立调用的脚本。产品上下文的“命令接口”“JSON schema”和“文件保护规则”是唯一契约；本节只定义组件、实施顺序和验证引用。

###### 架构与组件

- **`todo.py` CLI**：用 `argparse` 解析必填 `--data` 与四个子命令，调用 store 并把成功输出写 stdout、错误写 stderr/非零退出。
- **`TodoStore`**：读取、验证、变更和原子写 JSON；提供 `add`、`list`、`complete`，由 CLI 渲染导出。
- **测试**：每个命令走临时文件；用 patch/受控目录模拟替换或路径失败，不读取旧项目实现。

###### 关键设计决定

- **标准库单文件**：`argparse`、`json`、`pathlib`、`tempfile`、`os` 足以满足 CON-001；不引入包管理或服务。
- **先验证后替换**：store 在任何写前完成 schema、UTF-8 和路径校验，并把原子写封装为单一路径；代价是失败消息较多，换取不破坏既有字节。

###### 数据模型 / 关键实体 *(Feature 涉及数据时包含)*

持久化字段、值和顺序唯一见产品上下文“JSON schema”；实现不另定义格式。

###### API / 接口契约 *(Feature 暴露 CLI 表面时包含)*

参数、输出和错误语义唯一见产品上下文“命令接口”；`todo.py` 不增加隐式默认数据路径。

###### 时序与数据流 *(适用性说明)*

命令解析 → 读取/验证 → 内存变更或渲染 → 必要时原子写 → 输出。失败分支在替换前退出；没有并发、网络或重试协议。

###### 横切质量设计 *(适用性说明)*

对相关文本输入和存储字符串用严格 UTF-8 可编码性检查；对 JSON 解码错误（包括过深或递归错误）拒绝读取。导出先拒绝规范化路径或 symlink 别名；两条已有路径再用 `samefile` 拒绝 hardlink 身份相同。写入在目标目录进行，失败清理本次临时文件；hardlink 拒绝和写入失败测试分别验证数据文件与既有输出字节不变。

###### 风险与取舍 *(Feature 存在实质风险时包含)*

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 损坏/恶意 JSON 或 surrogate | 误读或再次写坏文件 | schema、JSON 解码与严格编码检查；失败不写 |
| 路径别名或替换失败 | 覆盖数据或残留临时文件 | 规范化/symlink/`samefile` 检查、同目录临时写、模拟失败测试 |

###### 需求覆盖

唯一的 AC → 设计 → Task → 检查关联见下方“实施计划”的“需求覆盖”；本节组件说明仅供该关联引用。

##### 实施计划

**关联设计**：本上下文“架构设计”

**已确认需求**：同上；**状态**：Draft（NOT_RUN）

###### 背景

按完整用户价值和共享写入边界切成两个纵向 Task，不按每个子命令机械拆分。两项由同一实现者持续负责；这只是本样例的切分，不是固定 Task 数量。

###### 目标 / 非目标

- **目标**：实现 AC-001–AC-004、实际测试和独立 Validate 所需的清晰证据。
- **非目标**：同步、并发协作、格式化无关文件或以覆盖百分比替代错误保护。

###### 技术栈

- Python 3 标准库；`unittest` 作为计划测试框架。版本、项目阈值和命令均 NOT_RUN，不能声称通过；若项目没有阈值，Validate 的 `correctness` 默认行 80%/分支 70%仍适用。

###### 实施层决定

- **选择**：Task 1 交付安全的 add/list 全路径；Task 2 交付其余命令和回归。**理由**：Task 1 有跨进程可见价值，两个 Task 都围绕同一 store，避免并发写同一文件。

###### 风险 / 取舍

| 风险 | 可能性 | 影响 | 缓解措施 |
|---|---|---|---|
| 先展示增量时跳过文件保护 | 中 | 高 | Task 1 的读/写保护和相关失败测试先完成；覆盖率汇总、格式化和提交收尾可在展示后完成 |
| 重新跑同一检查只为报告 | 中 | 低 | Build 保留受影响检查；独立 Validate 在最终快照运行必要套件，一次全量覆盖命令可同时作为套件证据 |

###### 实施阶段

- **阶段 1 / Task 1**：创建 `todo.py`、严格 store、`add`/`list` 和其数据文件的 UTF-8、JSON、surrogate、输入/数据路径、原子失败测试。最早可检验结果是两个进程的 add/list；可在覆盖率汇总、格式化和提交收尾前展示，但中途消息必须给出实际命令、版本、工作树和剩余限制，不能把 Task 标为 done。
- **阶段 2 / Task 2**：完成 `complete`、状态筛选、Markdown export、重复完成不写入，以及导出路径/symlink/hardlink 保护，并加入命令回归和全部 AC 的测试。
- **阶段 3**：Build 保留有意义的 TDD/累计检查；独立 Validate 在最终源码/配置快照执行所需测试、覆盖/类型/构建检查。相同独立覆盖率命令若实际跑完整相关 unit suite，可记录一次；Build 通过不是 Validate 证据。

## 有实质 UI 选择：提问、候选和反馈

用户要做待办 UI，但没有说明首版如何组织内容。产品 Agent 先复用已有信息，只把会改变导航、规则和验收的选择交给主 Agent：

> 首版按顺序显示待办，还是按项目分类？我建议先按顺序显示：可以更快让“添加 → 完成 → 筛选”成为完整旅程；项目分类还需要导航、编辑和迁移规则。这个选择影响候选原型和 REQ-010 的验收场景。

主 Agent 用已有原生交互询问。若用户没有回答，项目分类保持 `OPEN-010`，只继续不依赖它的布局或调研；不得把推荐写成 `confirmed`，也不得推进依赖分类的验收。

如果用户回答“首版这些组织方式按你的推荐”，产品上下文可记录：

#### DEC-010: 首版采用顺序清单

- **状态**：confirmed
- **决定**：按加入顺序显示待办，不提供项目分类。
- **用户证据**：用户明确委托“这些组织方式按你的推荐”；实际采用“顺序清单”。
- **范围影响**：项目导航与编辑规则仍在范围外。

这记录的是委托和实际采用项，不能改写成“用户亲自选择了顺序清单”。“继续执行”或“全程推进”本身也不能生成这一条。

适用原型策略时，产品/规格阶段可以展示候选，而不把它当成生产通过：

> 候选原型 v0.1：打开 `prototype/index.html`，尝试“添加一条待办 → 标为完成 → 用状态筛选”。本次检查只覆盖本地模拟数据和该旅程；没有服务端持久化、权限或同步。请在完成后返回列表，确认筛选结果是否符合预期；若不是，请指出“完成后留在当前筛选”或“回到全部”。
