# 产品上下文：REQ-human-validation 按需人工验收与自主推进

需求和计划对齐、实施获授权后，Agent 自行推进并验证；可以可靠自验证的修复和功能无需用户试用。确需真人判断时，再交付可操作的候选、步骤和待确认事项。

负责人可查看已验证内容和剩余缺口；首次只等待约定的人工观察时保持待验证，曾通过的版本在必要重验缺证时不能继续沿用旧通过。

### 用户场景与测试 *(必填)*

#### 用户故事 1 - 从已授权的计划持续推进（P1）

负责人对齐一次工作与授权后，能让 Agent 完成常规交付，并核对真实进度。独立验收可用同一任务的实施授权与仅规划授权两种输入，检查下一动作和证据。

1. **SCN-01** **给定** 需求、计划和依赖已对齐、完整任务已登记，且实施获授权，**当** 规划被接受或范围内发现需修复的问题，**则** Agent 自行进入 Build 或继续修复与适用验证。阶段切换和普通实现决定不产生额外的继续授权请求。
2. **SCN-02** **给定** 用户只授权规划，**当** 计划被接受，**则** Agent 交付计划，Build 和实现写入未开始。**给定** 某一步缺实质决定、外部授权或必要前提，**当** 下一动作依赖它，**则** 说明具体缺口及受影响动作，继续独立且已授权的工作。例如，试用反馈通过后，仍待外部授权的发布动作保持待授权。单独查询状态时，生命周期没有写入。
3. **SCN-03** **给定** 可复现 Bug 修复、接口功能、按明确判据检查的 UI 改动各有适用环境，且均无人工义务，**当** Agent 取得可靠的复现及修复证据、请求与响应证据或真实 UI 检查证据，**则** 直接完成适用验证并继续后续阶段，用户无需试用。若某项检查缺环境或可信证据，状态显示该缺口，保留适用的独立检查要求。

#### 用户故事 2 - 在可识别的候选上体验并反馈（P1）

确需真人时，负责人能从同一对话找到候选、操作和提交判断的方式。独立验收可对一次候选交接分别输入等待、通过和拒绝，检查实际结果。

1. **SCN-04** **给定** 用户要求亲自验收一个可自动检查的页面，或当前条件约定真人验收，或验收需由指定人判断交互是否顺手，**当** 对应旅程经适用预检后可体验，**则** 对话交接给出可打开入口、候选身份、步骤和预期、已检查项与缺口、负责观察的人及具体问题。提前展示的未提交候选和模拟结果按实际身份标示。
2. **SCN-05** **给定** 初次正式验收的其他必要检查均已通过，唯一待项是约定的真人操作或答复，**当** 用户尚未试用、仅回复“继续”或经过普通等待时限，**则** 继续显示待验项、候选及接续方式，`validation.result` 保持 `pending`。获得适用的真实通过证据且满足其余条件后才可记录正式通过。
3. **SCN-06** **给定** 本轮人工明确判定未通过、本轮验收已结束但缺必要证据，或另一项必要检查失败或受阻，**当** 汇总验收，**则** 按既有规则记录 `fail` 和实际归因。已有 `pass` 的工作在必要重验中遇到缺证据或未通过时，旧通过失效。若失效记录因前置条件被拒，保留事实并停止该 Feature 的后续调度，旧通过不得用于继续评审或发布。
4. **SCN-07** **给定** 两个 Feature 在同一候选上联合试用，**当** 负责人用自然语言或截图说明 A 对应项通过、B 对应项需修复，且仍有一项集成行为未检查，**则** A 和 B 各自可追溯到自己的判据和原证据，B 显示反馈与处理结果，集成缺口仍可见。

**文本原型走查**：按编排 brief 使用 `sdlc-prototype` 的 `inspect` 模式，范围是本次对话中的 SDLC 用户旅程。按 2026-11-19 计划中的“给人的验收卡片”和状态查询示例，依次核对打开候选和执行步骤（SCN-04）、等待时读到缺口和接续方式（SCN-05、06）、按 Feature 提交反馈（SCN-07）、续接时复用适用结论（SCN-08、09）。已有对话入口、卡片字段和状态说明覆盖这些动作。本次无待选视觉方向或新界面，文本检查足以收敛此规格，无需 HTML 或再次确认已接受的选择。走查证据限于文本，实际打开候选、用户体验、宿主续跑和正式验证留待执行后按实记录。[外部规划](../../../../workspace/20261119-sdlc-human-acceptance/PLAN.md#给人的验收卡片)

#### 用户故事 3 - 按原证据和授权跨上下文续接（P1）

续接者能恢复正确的候选、判据与责任，避免让人重复作答。独立验收可用有原答复的续接快照和有漂移的变体，检查状态解释、证据复用和必要重验。

1. **SCN-08** **给定** 新会话或新 clone 可找到同一候选、仍适用的环境及判据、原授权和负责人的明确答复，**当** Agent 恢复工作，**则** 复用已确认部分并继续剩余工作。进度说明按实际状态和宿主证据报告，若已暂停、无法续跑或运行状态未知，则如实说明。
2. **SCN-09** **给定** 试用后候选、环境、相关配置或判据变化，**当** Agent 核对新旧证据，**则** 指出变更及影响，重验受影响项，保留仍有适用依据的证据。仅版本标识变化且有可核对的等价证据时，可说明复用理由。
3. **SCN-10** **给定** 跨会话核对显示 `stale`，已批准原文可找回且与保存的指纹一致，变化仅为追加证据，**当** 有权责任人确认仍在原批准范围并显式重记，**则** 原答复与批准归属可追溯。已有适用委托的主 Agent 可按委托执行，原批准责任人保留此决定且无适用委托时由该责任人批准。
4. **SCN-11** **给定** 只有旧哈希而缺原文、批准来源无法核实，或行为、接口、验收义务、实际批准范围有实质变化，**当** Agent 拟沿用旧验收，**则** 说明受影响部分和缺口，只停止依赖该结论的动作，按既有规则取得必要决定或重验。单纯 `match` 无法证明实际检查或授权，业务 commit 相同也无法覆盖新义务。
5. **SCN-12** **给定** 旧 v3 工作区有既有记录，部分验收点无绑定指纹，**当** 查询或恢复原验收，**则** 仍可读取和按既有流程解释记录。`missing` 如实显示为未绑定，历史指纹没有自动补写，原验收义务仍然适用。

#### 边界情况

- 用户主动看候选可用于收集意见。是否属于正式验收条件以 DEC-001 及当前约定判断。
- 等待同一人工答复期间，保持候选可识别。独立的已授权工作可继续，变化或无法隔离时说明受影响的操作与证据。
- 状态说明是当前证据的快照。生命周期阶段、已有 checkpoint 和早期试用结论各有适用范围。

### 需求 *(必填)*

#### 功能需求

- **REQ-001 连续推进与验证方式**：在已对齐的范围、任务依赖和适用授权内推进。按 DEC-001 为验收项明确验证方式与依据，可引用已有判据。缺环境、访问条件或可信证据时按实际缺口处理。实质决定或授权确有缺口时，集中交接可一起判断的问题，只暂停依赖该缺口的工作。显式暂停、取消、失败非收敛及独立验证按 CON-001。来源 NEED-001、DEC-001、CON-001。
- **REQ-002 候选交接**：真人观察进入 Validate 的适用环节，Build 可提前展示。先完成适用预检，在已有对话用简短文字给出旅程及 Feature、入口、可核对候选、操作及预期、已检查项与缺口、观察者与反馈方式。候选固定或隔离后续修改，无法固定时说明限制并标明影响。模拟或早期候选的证据只在实际覆盖范围内使用，正式验证关联符合既有条件的候选和证据。来源 NEED-002、CON-001。
- **REQ-003 等待与失效**：首次正式验收的其他必要检查均通过且只待约定的真人操作或答复，保留 `pending`，在既有工程记录注明待验项、候选与接续动作。沉默、普通超时、模拟、自动检查或泛化的继续授权均不能充当必要的人类观察。等待本身不结案，也不触发重复催问或无变化的重验。明确拒绝、本轮验收结束仍缺证据或必要检查失败或受阻时，沿用 `fail` 及实际归因。已有 `pass` 的必要重验未通过或缺证据时撤销旧通过，保留适用的既有下游失效规则。若记录被拒，保全证据并停止该 Feature 后续调度。来源 NEED-001、NEED-002、CON-001。
- **REQ-004 反馈与多 Feature 证据**：接收现有方式提交的反馈，逐项记录候选、环境、观察者角色、对应验收项、实际观察、结论及处理结果。区分通过、拒绝、待处理和缺证据，范围内修复继续。联合试用可引用同一原证据，各 Feature 独立关联适用条件、覆盖与集成缺口，保有自己的状态和验证义务。跨 clone 引用须能定位到已同步的原证据。来源 NEED-002、CON-001。
- **REQ-005 状态解释与恢复**：主 Agent 依据所选 Feature 实际状态、已有工程记录和可用 checkpoint，显示当前阶段、候选、已检查内容、待项及下一步。待体验等为对话说明，CLI `next` 仍按现有状态和 Task 路由。恢复核对候选、环境、判据、原授权和明确答复，复用实际适用的证据；变化时只重验受影响项。当前执行和自动续跑能力只按实际宿主证据说明。来源 NEED-001、NEED-002、CON-001、CON-002。
- **REQ-006 上下文指纹与批准归属**：引用旧结论前沿用现有指纹核对和语义适用性检查。`match` 表示绑定内容一致，`missing` 表示未绑定，`stale` 先暂停依赖动作。要认定仅追加证据，须找回与已存指纹相符的批准原文，对照当前对象、范围和判据。覆盖仍有效时由有权责任人显式复核及重记，保留原批准来源。主 Agent 只有在适用授权或明确委托覆盖对应验收点时才可执行其职责，历史保留给原批准责任人的决定仍由该责任人作出。原文、来源或适用性不能核实时保留缺口。实质变更走既有决定与重验流程。重记继续使用实际验证与评审证据，发布仍依据实际授权及发布验证。来源 CON-001、CON-002。
- **REQ-007 兼容性**：更新后的流程可读取和续接既有 v3 工作区。原验收义务继续适用，缺少历史指纹沿用既有处理语义。产品范围或验收义务需变更时使用现有变更流程。来源 CON-002。

#### 关键实体 *(功能涉及数据时包含)*

- **验收项**：某个 Feature 的条件、适用环境、验证方式与通过判据。
- **候选**：可识别的实际版本或快照，可能供多个 Feature 联合体验。一次观察按实际覆盖关联各自的验收项。
- **观察和批准**：观察是有责任人及适用范围的事实或反馈。批准分别适用于具体决定、验收点或外部操作，原来源随结论保留。

### 成功标准 *(必填)*

#### 可衡量结果

- 已对齐且获授权的代表性旅程中，由阶段切换、普通实现选择、已答且仍适用的事项产生的重复确认次数为零。仅规划授权的样例中启动 Build 和实现写入均为零。覆盖 SCN-01 至 SCN-03、SCN-08。

- 恢复与兼容样例能指出证据所覆盖的版本、环境、验收项及批准归属。证据不适用时影响范围和恢复动作可见。覆盖 SCN-08 至 SCN-12。

## 发布后观察计划（SDLC 补充）

- **观察条目**：可比 SDLC 任务中的重复确认次数、授权到首个可体验候选的时间、用户验收耗时、验收后发现的缺口。
- **基线或未知原因**：暂无可比运行证据，时间和质量变化待观察。
- **目标或判断方式**：依据成功标准检查零重复确认、必要验收证据与恢复正确性。涉及时间或质量变化的判断使用可比案例，有样本限制时据实说明。
- **观察窗口**：自发布至首轮有可复核的实际 SDLC 使用案例。
- **负责人**：该轮交付的主 Agent 汇总可用记录，实际观察者提供适用反馈。
- **反馈回流**：将影响产品行为或验收义务的反馈按既有范围变更流程纳入后续 Requirement。
- **确认来源/关联决定**：外部规划中的结果观察建议及 NEED-001、DEC-001。观察安排仅作为本规格的后续观察计划。
