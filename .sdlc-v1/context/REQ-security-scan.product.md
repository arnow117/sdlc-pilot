# 产品上下文：REQ-security-scan 安全扫描接入

## 已确认的需求：在 SDLC 使用 Codex Security

**Requirement ID**：`REQ-security-scan`
**状态**：已捕获；生命周期进度以 state 为准
**来源**：2026-11-15 当前对话及已有 Codex Security 源码调研。

### 权威规则

- 用户明确提出的需求是绑定输入；工程默认不伪称用户逐项选择。具体扫描工具、模型、范围和预算按当前任务的授权确定。

### 需求

1. **NEED-001，confirmed**：把 Codex Security 的扫描机制接入 SDLC 的 validate/review 工作，能够对需要安全验证的变更运行并消费扫描结果。来源：“整体对这个做引入式继承（在 review 或者 validate 阶段怎么 run 一波这样的）”“集成一波吧”。
2. **NEED-002，superseded**：此前要求缺少依赖时强烈建议安装；用户后续要求改为按需提示，由 NEED-004 替代。
3. **NEED-003，confirmed**：控制 Token 消耗，区分范围、执行与实际验证结果。来源：用户先询问扫描 Token 消耗，之后接受按风险定向扫描、review 复用同一结果的建议并要求实施。
4. **NEED-004，confirmed**：实际需要使用 Codex Security 时才检查当前执行机器；缺少依赖或配置时正常提示安装或配置，不在每次进入 SDLC 时主动检查或强烈提醒。来源：“不用这么强，就是 sdlc 运行时按需提示好了（比如到了验证阶段）”。

### 约束与决定

- 扫描默认按具体安全风险和验收义务选择，不把所有 Feature 自动升级为付费全仓扫描。validate 消费实际扫描证据；review 复核同一版本的证据和缺口，不默认重复扫描。
- 沿用现有 lifecycle 状态与四类验证归因；依赖缺失、未运行、未完成、范围不足或凭据不可用不得写成扫描通过。认证状态未检查时写未知，不能从 PATH 判断已配置。
- 使用 Codex Security 前的按需依赖检查只读、不执行扫描、不自动安装或登录；未选择该工具时不执行该检查或提醒。普通 SDLC 工作可继续，选中的必要安全验证则必须等待真实可用工具和证据。
- 本次用户要求由当前会话继续完成迭代；实际执行者和不能独立完成的验证/评审如实记录，不将串行自查称为独立检查。
- 已有外部资源消耗约束继续适用：真实模型扫描及运行环境/镜像下载前先明确范围、模型、预算、并发、收尾并取得确认。

### 范围外与开放问题

- 本次不自动修复漏洞、发布结果或修改第二套生命周期状态；不默认下载、登录、部署或对外调用模型。
- 真实模型、认证、真实费用和目标机器的扫描效果尚未验证。实际扫描需在相应环境与授权具备后验证；不把合成测试外推为真实安全扫描通过。

### 确认日志

- 2026-11-15：用户接受接入并要求当前会话实施，随后将强烈安装建议调整为需要使用时的普通提示；NEED-004 替代 NEED-002。具体工程实现依据仓库契约作选择。

## 功能规格：安全验证与依赖提示

**关联 Requirement**：`REQ-security-scan`
**输入**：用户请求、`project.md`、现有阶段/验证方式及此前源码调研。

### 用户场景与测试

1. **依赖提示**：给定本机没有可发现的 Codex Security CLI 且没有已确认可用的插件能力，只有当当前阶段需要使用 Codex Security 时，才指出具体缺口并提供官方安装入口；不触发下载、登录或扫描。普通 SDLC 工作及选择其他扫描工具时不做该工具的检查或提醒；执行环境变化时重查。
2. **不确定能力**：给定路径上只发现可能与其他工具重名的短命令，或 CLI 存在但认证/版本未检查，应分别标为候选或未知，不能声称已配置、可扫描或没有安装。插件能力由宿主实际发现结果确定，不由 CLI 缺失推断。
3. **安全变更**：给定认证、权限、敏感数据、外部输入或供应链等变化，计划/验证阶段评估受影响边界和所需扫描能力；选择的工具和预算应覆盖实际验收，不强制所有安全工作使用付费模型。
4. **扫描成功与缺口**：真实扫描完成且产物、范围、版本及必要证据满足当前要求时，验证者按现有规则汇总；未运行、空结果无覆盖证据、超时、超预算、缺失工具、产物不完整或不适用等均不能自动算通过。
5. **Review 复用**：给定当前验证版本已有适用扫描证据，review 核对来源、覆盖、发现和不确定性；发现实质缺口时提出针对性补验，不自动再运行一次同样的模型扫描。

### 需求

- 提供可复用的 `security-scan` 验证方式和 Codex Security 接入说明；与现有角色和其他验证方式区分。
- 检查结果与扫描证据应保留真实来源、执行状态、版本/范围、失败原因和必要的覆盖缺口；不输出凭据或把检测结果写成第二份状态源。
- 原生扫描的退出状态与 SDLC 结论分开判断，遵守既有 `PASS`、`IMPLEMENTATION_FAILED`、`ENV_BLOCKED`、`INCONCLUSIVE` 规则。

### 成功标准

- 本地可重复检查至少覆盖：CLI 缺失、检测到长命令、只有可能重名的短命令，以及输出中不泄露环境变量值；探测不执行外部候选命令。
- 路由、依赖提醒、验证、评审和安装说明可从打包后的技能路径发现；仓库现有结构检查与相关回归通过。
- 使用无模型的本地测试核对失败与缺口处理；真实 CLI、认证、模型调用和扫描效果只有实际运行后才报告。

### 范围外、假设与依赖

- 范围外同上。扫描器、模型凭据和相应供应商服务是可选外部依赖；具体可用性不能由源码检出、路径存在或测试替身证明。
- 保留现有状态版本与 `record-validation` 字段；扩展真实扫描结果的通用机器规范化能力如被发现需要独立迁移，应先界定其兼容性和范围。
