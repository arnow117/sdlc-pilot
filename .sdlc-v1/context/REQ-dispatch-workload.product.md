## 问题、用户与期望结果

使用 SDLC 的主 Agent、阶段执行者和仓库维护者，需要在保持质量与权限检查的前提下，减少固定规格小项目的阶段启动、重复读取、Task 正式交接、无稳定事实变化的 Onboard，以及重复生成检查和交付报告。只缩短规则文字而继续生成同样对象，不算完成。

期望结果：符合条件的小项目只派一次准备工作；完整实现由同一 Terra 连续完成并及时展示真实增量；稳定项目索引按事实变化刷新；验证与交付复用适用证据。逻辑阶段、独立验证/评审和主 Agent 接受职责保持完整。

## 授权范围与非目标

范围内：

- 在现有编排协议中定义有界 Backlog/Spec/Plan 候选准备批次，分别接受候选并按原 CLI 顺序应用状态操作，支持部分成功后的准确恢复。
- 小项目优先一个完整 Task；中间里程碑只报告真实结果，完整验收后才请求 done。修正仍由原实现者负责。
- PROJECT 维护稳定入口、命令、环境、资源、surface 与长期来源引用；代码、测试数、覆盖率或 HEAD 变化本身不触发刷新。
- 按目的与输入适用性复用检查、旅程资产和交付证据；明确专业视角与运行时模型角色，保留独立 Terra Validate 和 Sol Review。
- 同步确有冲突的 router、adapter、阶段技能、模板和示例；权威编排规则仍仅定义在现有 stage-agent-protocol。
- 在唯一隔离源码副本实施并验证，CHANGELOG 记录 Unreleased；本轮验证和评审可以针对未提交快照进行，正式 commit 绑定保持 pending。

范围外：

- 改变 lifecycle_state.py、公共 CLI、state_version=3/schema、Requirement/Feature/Task 状态语义或 roles/modes 字典。
- 添加 Issue、运行时服务、inbox、第二状态源、持久化结果格式、进度账本或用户项目迁移。
- 修改旧项目、安装缓存、全局配置或无关未提交改动；提交、推送、PR、tag、release、插件升级和新模型实跑。
- 降低质量、独立性、授权、非收敛停止或必要重验要求；承诺固定用时或以未实跑的派工数量宣称提速。

## 已确认规则

1. 准备批次仅适用于已授权、边界明确的单仓/单模块小项目。存在未决产品选择、needs_selection、待确认原型、外部授权缺口或复杂接口/迁移/并发风险时，保留所需常规阶段。本次改动属于结构 evolve，落地前仍遵循现行协议，不能预先使用拟新增批次。
2. 批次只合并派工；原 canonical stage result、阶段接受与 CLI 前置条件仍逐项成立。失败即停止后缀；恢复只处理首个未接受阶段或未应用操作，不能重复创建已成功的记录，也不能因部分 Task 登记成功而提前 Build/Validate。
3. 已有 ready Requirement 或 Feature 不重复 capture/start。确切 ID、operation 和长参数来自当前已核对契约；不猜别名、不执行未来占位值。
4. 保持 Sol/xhigh 决策、规划、接受和独立 Review；Terra/xhigh 实现及修正，另一位 Terra 实际独立 Validate。角色卡的专业视角不能代替运行时模型路由。
5. 只有入口、命令、配置、surface 或相关稳定事实改变才刷新项目索引；实际运行数、覆盖率、候选版本和阶段状态保留在既有工程记录/state。预期事实明确 planned/NOT_RUN，历史出处不能冒充当前通过证据。
6. 同目的、同相关输入的证据可复用；源码、测试、runner、配置、环境、相关使用契约变化，或失败、缺证据、独立阶段义务，均要求相应实际检查。完整 coverage 执行相同 suite 时可兼作 unit；Build pass 不能代替独立 Validate。
7. Ship 只使用当前批准源、最新正式证据和明确授权，保留来源/内容核对、新目录真实 smoke 与正式 commit 关联。未获提交发布授权时，不伪造正式验证、评审或发布状态。

## 验收条件

| ID | 可观察条件 |
|---|---|
| AC-1 | 合格小项目允许同一 Sol 一次派工返回有序的三个阶段候选；不合格输入保留所需常规阶段，不从沉默推断产品选择或授权。 |
| AC-2 | 主 Agent 逐块核对并接受结果；正常顺序与部分操作失败后的隔离 CLI 演练证明：不重放成功操作、后缀停止、Plan 的全部 Task 及依赖登记完整才开始执行。 |
| AC-3 | 一个完整 Task 的真实增量可以提前展示且不中断原实现者；里程碑不请求 done、不改变 Feature/发布状态，独立交付边界仍可拆 Task。 |
| AC-4 | 普通代码修复但稳定索引事实未变时，project_candidates 为 [] 且不派修复后 Onboard；真实稳定事实变化仍由指定写者刷新。 |
| AC-5 | 同输入完整 coverage 的 unit 目的不重复执行；只因提交身份出现不重跑同套检查。输入变化或失败时执行受影响检查，独立 Terra Validate 实际运行当前候选。 |
| AC-6 | 已有 subprocess/旅程资产优先复用；确有缺口才补一次，后续只补新边界。错误检查保留失败归因并局部重跑，证据不重复粘贴。 |
| AC-7 | adapter、brief、阶段结果明确模型职责、确切参数与实际版本/命令；缺失、歧义和错误照常补正，失败历史及现有停止规则保留。 |
| AC-8 | 交付来源、授权、正式证据和新目录 smoke 的职责明确；不重跑同目的完整 suite/coverage，不重写整份工程史，最终汇总引用一次记录的证据。 |
| AC-9 | 结构检查、diff 检查、实际 CLI 隔离场景验证及独立评审覆盖上述范围、规则和验收条件；静态走查、临时 fixture 与真实模型实跑明确区分。 |
| AC-10 | 公共 CLI、schema、插件版本元数据和旧项目保持原样；只保留授权范围内未提交修改，正式 commit 验证/评审绑定为 pending，无提交发布。 |

### 具体边界示例

下表细化已有 AC，不增加验收范围；这些是待后续验证的场景，不是通过记录。

| 对应 AC | Given / When / Then |
|---|---|
| AC-1 | Given 单模块且产品选择和授权已明确，When 准备派工，Then 同一 Sol 返回三个有序候选；若出现 needs_selection 或待确认原型，则先解决该边界，不接受依赖它的下游候选。 |
| AC-2 | Given capture/ready/start 与 Task A 登记已成功、Task B 登记失败，When 恢复，Then 核对实际 state/context/Git，只补未成功操作；全部计划 Task 和依赖核对完成前不开始 Build/Validate。 |
| AC-3 | Given 一个 Task 已实现 add/list，但 done/export 尚未完成，When 展示真实增量，Then 原 Terra 在原授权内继续，不请求 Task done，不作正式交回。 |
| AC-4 | Given 仅代码修复、测试数和 HEAD 变化，When 核对稳定入口与命令等事实仍相同，Then 返回 []；若实际启动命令改变，则由指定写者刷新对应事实。 |
| AC-5、AC-6 | Given 完整 coverage 已运行相关 suite，When 仅提交身份改变且相关输入等价，Then 复用同一 unit/coverage 证据并关联版本；若 runner 或相关使用契约改变则做受影响重验，已有旅程资产继续复用，独立 Terra 仍实际检查当前候选。 |
| AC-7 | Given brief 选择 qa 视角并要求独立 Terra，When 实际执行者为 Sol 或结果缺少确切版本，Then 不能以专业视角或旧证据补足独立性，须按实际缺口补正。 |
| AC-8～AC-10 | Given 用户仅授权未提交验证，When 检查通过并准备汇总，Then 引用实际快照证据、正式绑定仍 pending，不提交或发布；未来另获交付授权后，仍核对批准源与内容并做新目录 smoke，不能拿静态走查宣称真实模型实跑。 |

## 工作量结果与观察计划

- **基线**：已批准报告记录原案例 21 个子轮次及其重复对象；这是该次复盘事实，不能推定为所有项目基线。
- **本轮判断**：检查规则与实际隔离 CLI 证据是否兑现 AC-1～AC-10；记录必要的阶段候选、Task 交接、稳定索引刷新、旅程资产、检查和交付证据的变化，避免只改文案。
- **后续观察目标**：无修复路径约六个有界子轮次（稳定索引已准确时可省刷新）；保留原例两次真实修复时约十二轮。这是报告的规划参照，不是固定上限或已实测结果。目标包括错模型额外验证与纯参数补正为零，真实错误仍须纠正。
- **观察窗口与负责人**：维护者在本轮未提交验证/独立评审中核对行为；后续用户另行授权对照实跑时，主 Agent 按报告第 6 节记录首增量、全程墙钟与生成量。当前实跑用时改善为 NOT_RUN，不启动模型消耗任务。
- **反馈回流**：验证缺陷回到本 Requirement 的既有工程证据并由原实现者修正；超出范围的新产品结果另建 Requirement，仍使用原 state/context，不新增观察服务或账本。

## 依赖、确认与未决问题

依赖：现有 CLI 与 state_version=3、当前阶段协议、普通 Git/Markdown，以及隔离 CLI fixture 和已有 subprocess/旅程检查资产。没有其他 Requirement 依赖。

产品范围、方案选择、角色分工和未提交交付边界均已由用户批准；没有未决产品选择。具体编辑、场景组织与证据位置由后续 Plan 收敛。此需求为内部编排行为改进，场景已明确且无 UI 选择，不需要原型。本次 Spec 仅确认产品规格足以进入规划，不代表实现或正式验证通过；ready 状态由主 Agent 接受后通过现有 CLI 更新。
