# 视觉系统：每个产品确定自己的外观

## 制作前的简短设计约定

沿用已有 DESIGN.md；新原型记录以下内容即可，无需另启完整设计流程：

| 决定 | 内容 |
|---|---|
| 使用情境 | 谁操作、主要任务、设备宽度、连续阅读还是高频处理 |
| 产品形态与参考 | 移动 App / 响应式 Web / 桌面后台；参考中继承的布局、导航、视觉元素以及主动调整项 |
| 视觉方向 | 一句话说明产品的气质和与使用情境的关系 |
| 色彩 | 页面/面板底色、主次文字、品牌主操作、边框、成功/警告/错误 |
| 字体 | 标题、正文、数据的字体与字号层级；离线交付的 fallback |
| 布局 | 内容宽度、导航方式、网格、留白和窄屏折叠方式 |
| 组件 | 按钮、表单、标签、表格、弹窗的共同约定 |
| 特色 | 一项与产品有关的视觉细节，例如书脊、索书号或真实对象结构 |

特色来自产品内容，不以每页增加装饰实现。平台与客户端共享品牌和语义色，各自定义密度和组件尺寸。不要把原型演示控制混进正常产品导航。提供多份参考时先对比每端的产品形态，不能混合成一套通用响应式网页。

## Token 与组件

按语义命名，例如 `--surface`、`--surface-raised`、`--text`、`--text-muted`、`--border`、`--primary`、`--success`、`--warning`、`--danger`。颜色值根据当前产品选择，避免每个组件随意写一组新值。

- 正文和表单以目标设备可读性为准。可从 14–16px 正文、12–13px 辅助文字开始验证；不要为塞进手机外壳而整体缩小。
- 标题层级清楚；数据表金额和数量采用易比较的数字对齐方式。
- 同一种动作复用相同组件样式。主要操作、次要操作、破坏性操作和状态标签各有含义。
- 按钮覆盖默认、hover、focus、disabled、busy；输入覆盖空、已填写、错误、disabled。按组件实际用途实现，不机械给每个元素添加所有状态。
- 表单错误放在字段附近，并提供可执行的修正提示。禁用状态说明必要前提。
- 图标使用一致的线条与尺寸；关键操作有文字或可访问名称。避免把 emoji 当作整套操作图标。
- 只用颜色不能完整表达状态；同时给出文字或图形线索。

## 两端布局

客户端：当前任务与主操作容易找到，信息按旅程展开。移动 App 保持触控导航、子页层级与移动内容宽度；手机外壳属于可选预览，实际内容需适应目标宽度。只有明确采用桌面客户端或响应式 Web 时，才利用大屏扩展信息列数。

平台：先表达待处理对象与操作上下文。列表过滤区、表格、详情的密度一致；需要滚动时让范围明确。小屏优先折叠导航、减少网格列或采用局部横向滚动，不缩小整页文字。

相同对象的标签、状态颜色、名称和单位在两端保持一致；布局与控件密度无需一样。

将共享的品牌/语义 token 与各端的布局/组件 token 分开。检查客户端的字号或卡片调整是否意外影响后台表格、后台的紧凑控件是否意外缩小移动端触控目标。

## 反馈、动效与键盘

采用有目的的过渡：选中、展开、状态变化和操作反馈。普通操作可从约 150–250ms 起步；需要较长动画时验证不会阻碍操作。尊重 `prefers-reduced-motion`。

原生 button/input/select 优先；可见焦点不能只靠颜色细微变化。弹窗处理初始焦点、Esc、关闭后的焦点恢复；文字和长列表溢出有实际检查。

## 视觉验收

批量检查目标桌面与窄屏尺寸，查看完整页面和关键弹层。检查文字可读性、主要按钮、内容裁切、横向溢出、空态和错误态。将发现的问题合并修正后复查，不做无边界的样式微调。

截图必须是真实渲染证据。仅阅读 CSS 得到的是设计建议，不能据此宣称视觉验收通过。
