# 客户端 profile

适用于 App、移动 Web、桌面用户端。客户端不必都是手机布局。

## 先确定客户端形态

| 形态 | 导航与布局 | 适配方式 |
|---|---|---|
| 移动 App / 小程序原型 | 按任务选顶层 Tab、子页返回、底部操作；优先触控和单列内容 | 先验证约 360–430px 内容宽度、安全区域和不同高度；桌面展示保持移动内容宽度，可加预览容器 |
| 响应式 Web 客户端 | 根据各断点选择导航、列数和内容宽度 | 大屏可扩展为多列；窄屏重排而非整体缩放 |
| 桌面用户工作区 | 按持续任务安排侧栏、列表和详情 | 优先验证主要桌面尺寸；窄屏支持范围独立说明 |

根据用户说明和参考推断形态，不把“HTML 原型”理解成响应式网站。移动 App 的桌面预览容器属于展示层，移动设备上应让出边框和外部留白，内容使用可用视口。不要照搬参考中的固定 340×680 尺寸、小字号或不可滚动区域。

移动 App 重点检查：底部导航始终可达，内容最后一项不被遮挡，详情有清楚的返回入口，主操作适合触控；搜索、列表位置与输入在返回后保留。重要触控目标可从约 44px 开始设计，再按实际密度检查。大段宣传文案不应挤掉查找和处理任务的入口。

## 从用户任务决定页面

用“入口 → 操作 → 处理中 → 结果 → 下一步”梳理本次旅程。页面应表达用户关心的状态；相同业务对象在首页卡片、列表、详情和结果页中保持一致。

| 场景 | 应表达的内容 | 可观察的交互 |
|---|---|---|
| 首页或工作区 | 主要目标、待办和当前状态 | 卡片进入对应对象；切换不会串用另一对象的数据 |
| 列表 → 详情 | 筛选结果、对象标识、可执行动作 | 进入详情后返回，保留合理的筛选和上下文 |
| 表单/多步提交 | 必填项、约束、进度与提交结果 | 错误定位到字段；修正后可以继续；取消不提交 |
| 状态详情 | 当前阶段、发生原因、后续动作 | 状态改变时按钮与时间线同时更新 |
| 外部能力 | 系统前提、授权结果、失败恢复 | 可模拟拒绝、不可用、成功；不真实请求设备权限 |

只选择本产品需要的页面模式。不要因为样例有钱包、设备或 AI 就加入这些模块。

## 导航与层级

- 区分顶层导航、子页、弹窗和底部操作面板。返回关闭最上层，并回到原来的业务对象。
- 选择“完成”“返回”“取消”各自的目的地；避免用固定次数的连续返回来猜目的页。
- 提交后进入的结果页应能回到列表或继续下一步；不把用户留在过期的可提交表单。
- 切换标签、重进页面、关闭弹窗后，滚动锁定、焦点和选中对象保持合理状态。
- 移动布局覆盖目标窄屏宽度、长文本和底部安全区域；手机外壳只是可选展示，不替代内容区响应式。
- 桌面客户端按实际工作区域设计，不将所有内容压进手机外壳。

## 状态与恢复

对核心旅程列出真正会影响下一步操作的状态。例如申请的草稿、已提交、待补充、已完成；不要为凑齐“所有状态”创造业务流程。

- 加载时说明正在做什么，并防止重复提交；失败后保留可恢复的输入。
- 空态给出可执行入口；错误态给出重试、修改或退出方式。
- 撤销授权、解绑设备等前置条件变化，须明确影响哪些能力以及已有处理中事项。
- 可重试行为要定义剩余次数或无限重试的产品决定；如果有限次，连续失败和重新打开页面不能重置次数。
- 涉及金额、积分或配额时，明确单位、变化时点和终态，多个页面读取同一状态。

## 演示设置

可提供少量与本次旅程相关的场景，例如“新用户”“已有待处理申请”“模拟成功”“模拟失败”。场景选择使用确定性结果，避免随机成功率导致演示不可复现。

演示入口与用户正常操作分开。用户点击正常提交仍需经过真实的本地校验和状态转换；演示按钮用于选择外部结果或快进时间。

## 适用验收例

以下是行为写法，规则需来自当前项目：

- 给定申请已被驳回，当用户修正并再次提交，则同一申请显示新的提交记录，列表与详情显示一致状态。
- 给定表单有错误，当用户点击提交，则数据不变且错误可定位；修正后可以成功提交。
- 给定操作需要绑定设备，当用户取消绑定，则回到原任务并保持输入，不能显示任务已完成。
- 给定结果模拟仍在等待，当演示数据重置，则后续旧结果不改变重置后的页面和数据。
