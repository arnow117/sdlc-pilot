# 行为交接与 SDLC 接口

原型负责表达和验证产品行为。研发还需要知道哪些行为已确认、哪些只是模拟、哪些规则仍未决定。

## 交付物的最小组合

新建独立原型通常采用：

```text
prototype/
  index.html             # 单端入口，或双端切换入口
  product-context.md     # 行为、规则、场景、限制和版本记录
```

用户要求分别交付两端时可使用 `client.html`、`platform.html`。素材和截图只在实际需要时添加；已有工程保持其目录结构。用户只要 HTML 时，把交接摘要放入可复制的原型说明视图。

`product-context.md` 是内容示例名。已存在 PRD、产品上下文或 SDLC `product_context_ref` 时沿用权威文档，不建立同等地位的第二份规格。

## 内容骨架

按本次复杂度缩放；局部修改只更新受影响条目。

### 1. 范围和来源

- 产品目标、使用角色、本次覆盖和范围外内容。
- 原型版本、入口、查看方式、源文件/版本。
- 已确认决定的来源；观察行为、演示假设和未决事项分开记录。
- 离线与刷新行为；是否有持久化、是否有双端联动。

### 2. 场景与页面

| 场景 | 角色/入口 | 页面或控件锚点 | 操作路径 | 完成结果 |
|---|---|---|---|---|
| SCN-001 提交申请 | 普通用户/申请列表 | PAGE-apply | 填写 → 提交 → 查看详情 | 同一申请出现在列表和详情 |

每条核心场景有可复现的初始数据和可观察结果。需要时给 DOM 添加 `data-scenario` 或稳定页面 ID；不要求每个装饰元素都编号。

### 3. 实体、规则和状态

记录关键字段的含义与单位、枚举、状态转换、角色动作矩阵、错误反馈。已有领域术语和 ID 优先复用。

规则示例写成“对象处于已完成时不再允许提交处理结果”，而非只写“按钮禁用”。数值边界、次数、时效和保留期限应有来源；没有来源的演示值标为假设。

双端场景补充事件映射、状态显示映射和配置生效范围。API、数据库和队列实现留给后续工程规划；若用户明确要求接口设计，再单独列为候选。

### 4. 验收场景

使用 Given / When / Then 或等价中文。至少覆盖当前核心成功行为及相关失败/边界行为，不机械规定场景数量。

```text
SCN-002：拒绝重复处理
来源：已确认的“每个申请只接受一次最终处理结果”
给定：申请 A 已经处理完成，待办数量为 0
当：审核员再次尝试提交处理结果
则：显示该申请已处理；申请结果保持不变；待办仍为 0；
    不新增处理记录或重复业务副作用
演示数据：申请 A，已完成
原型入口：平台申请详情
实现程度：本地可交互
验证证据：实际执行步骤、结果和原型版本；未执行则明确写未验证
```

推断的规则可以作为候选场景供讨论，但不能填成“已确认来源”。

### 5. 实现程度、验证和变化

| 场景/能力 | 原型实现程度 | 产品确认情况 | 验证方式和结果 | 后续研发事项 |
|---|---|---|---|---|
| 提交申请 | 本地可交互 | 已确认/假设/待决定 | 静态/点击/未验证 | 服务端持久化等 |
| 外部结果 | 模拟外部能力 | 已确认/假设/待决定 | 实际结果或限制 | 接入外部服务 |
| 未覆盖能力 | 占位或不在范围 | 已确认/待决定 | 不适用 | 后续范围 |

这几个维度互相独立：已实现本地交互不表示产品已确认，产品已确认不表示已经点验，更不表示生产接口已实现。

记录目标视口、控制台异常和关键截图仅在实际检查时填写。保留变化摘要：本次修改的规则/场景、影响的两端页面、回归结果和开放问题。

## 接入 SDLC

### 项目已有 `.sdlc-v1`

在任务识别阶段，必要时只读检查 `state.json`、`project.md` 及相关引用，确认本次工作是否属于已跟踪 Requirement，或用户是否明确要求接入既有流程。确认相关后，再读取对应的 `product_context_ref` 和当前 stage，并读取包内的 [SDLC 原型适配](../../sdlc/references/integrations/product-prototype.md)。该适配是 SDLC 接口的唯一权威来源，不复制到本技能。否则按本技能独立交付，不能因为项目存在 `.sdlc-v1` 自动进入生命周期。

主 Agent 拥有编排与生命周期；当前 stage 和其 brief 仍定义本次原型工作的写入边界与验收。接入时沿用当前产品上下文模板和生命周期协议：已确认的意图与规则只写权威产品正文，原型观察、演示假设和开放冲突仍分开；原型技能不写 `state.json`，不标记 Requirement ready，也不创建 Feature/Task。产品上下文保存意图、确认状态、场景映射和原型 baseline；后续工程上下文保存实现/复用选择以及正式 validation/review 证据，并引用原始产物。

若包内适配缺失或链接无法解析，报告分发包缺口及其交付影响；不要发现、安装或恢复旧 `product-prototype` 技能。原型仍可在未跟踪任务中独立交付，也不得直接改动 SDLC 状态。

### 项目还没有 SDLC

交付原型和紧凑行为说明即可。用户明确要进入 SDLC 时，再由其入口按当前协议捕获需求和指定 `product_context_ref`。无需为了产出一个原型先初始化完整 SDLC 状态。

### 交接给研发的判断标准

研发应能据此回答：谁在什么前提下做什么、数据怎样变化、失败怎样恢复、哪些规则已确认、哪些行为只有模拟、用什么场景验证实现。缺失答案记录为问题，不用原型中的 UI 文案代替产品决定。
