# 审阅区、导览与回看

复杂原型的评审常常需要三样东西：一个和产品分开的位置来说明当前在哪一步、一条能重复走的路径、以及能把走错的路退回去的手段。本文件是这三项的权威定义；其他文件引用这里，不复制一份。

这些能力是**按需**的。小原型不需要审阅台，更不需要为此新建 HTML；只有评审确实要重复演示、需要解释入口、或者需要从错误分支退回时才引入。

## 先判断是否需要

| 需求 | 是否引入 | 说明 |
|---|---|---|
| 一次走完就够的简单原型 | 否 | 描述加正常入口足够 |
| 评审要重复演示同一条旅程 | 是 | 需要确定性场景与固定起点 |
| 评审方会问「这一步该看什么」 | 是 | 需要导览步骤和观察重点 |
| 评审会走错分支，需要退回 | 是 | 需要回看与已知起点 |
| 只是想把页面列出来 | 否 | 页面清单写进交接说明即可 |

引入前先回答：现有交付物里有没有等价能力？已有演示设置或状态层优先复用，不要为了审阅再建一套状态。

## 审阅区与产品隔离

审阅区不属于产品。它满足：

- 不出现在产品导航、底部标签或页面流转里；产品内的用户不会看到它。
- 不改变产品行为。产品操作仍走产品自己的业务动作；审阅区只**调用**它们。
- 不持有产品的私有状态。它读产品导出的派生值，写产品导出的动作。
- 审阅控件自身的样式与产品样式分开，避免产品改版时被误改或误继承。

需要「专注预览」时，隐藏审阅区而不重排产品布局。产品形态（移动 App、响应式、桌面工作台）由产品自己决定，审阅区不要求统一三栏，也不套手机外壳。

## 导览步骤的四种类型

导览的每一步标注类型。类型决定这一步算不算证据：

| 类型 | 含义 | 是否构成用户入口证据 |
|---|---|---|
| 准备 | 建立已知起点：重置到固定 fixture、选定角色或场景 | 否。是起点声明 |
| 状态注入 | 注入外部结果或演示状态 | 否。是模拟，不得冒充真实外部行为 |
| 产品操作 | 在产品里执行真实业务动作 | 是，但只在从普通入口走通时 |
| 观察 | 读取派生结果并与预期比对 | 是该状态的观察证据；不能单独证明入口路径 |

分开的理由：把「注入了一个状态」记成「用户走到了这一步」会让评审看到假的通过。

## 入口的三种证据

同一条旅程，三种到达方式的可信度不同：

| 方式 | 做什么 | 记录为 |
|---|---|---|
| 普通入口 | 从产品真实导航走完 | 该入口的（局部／模拟）旅程证据 |
| 审阅直达 | 直接跳到某一页或某一步 | 局部行为证据；须写明跳过了什么 |
| 注入步骤 | 由审阅区注入状态或外部结果 | 模拟证据；须写明注入内容 |

### 怎么写才不算虚称

- **用户操作确实从普通入口走过**：记为该入口的局部或模拟旅程证据。「局部」指这次只覆盖了声明的范围，「模拟」指外部结果是注入的。
- **外部结果由演示注入**：逐步写明哪一步是注入的、注入了什么。不得写「已发生真实外部行为」。
- **只是外部结果被注入**：不因此写成「未从普通入口走通」。用户操作走过了就写走过，外部结果是注入的就写注入，两件事分开记。
- **仅审阅直达**：不得写「普通入口已走通」。直达跳过的前置条件要写出来。

一句话：用户路径与外部结果分开取证，任何一方的缺失都不补到另一方头上。

## 确定性场景

场景使用固定 fixture、固定分支和固定顺序。同一场景重复运行应得到同一结果。

- 不用随机成功率。成功、失败、结果未确认等分支由评审显式选择。
- 不依赖真实时间、真实网络或真实账号。时钟如需推进，由产品自己的动作推进，不由审阅区直接改时间。
- 场景结束点明确：最后一步是什么、结束后产品停在哪。

## 时钟与重置

重置覆盖本原型拥有的业务状态、选中对象、导航、弹窗和本原型排的定时任务。审阅区只能取消自己排的任务；产品自管的任务由产品自己取消。

产品重置后仍可能到达的旧回调属于产品缺陷。防护方式由产品自己选：排任务时记下当时的场景版本，回来时版本已变就丢弃；或者把任务句柄登记下来，重置时逐个清除。两种做法都可以，不强制唯一一种，但产品必须让审阅区知道用的是哪一种。

审阅区不能替产品取消这类任务，也不能声称已经替它做了。

## 可复用的审阅资产

仓库提供一份可选资产：[review-console](../assets/review-console/review-console.js) 与配套的 [审阅面板](../assets/review-console/review-panel.js)。它是一个**适配器制**的控制器：产品提供适配器，控制器只调用适配器提供的方法，不接触产品私有状态。

适配器契约：

| 方法 | 必需 | 用途 | 成功时返回 |
|---|---|---|---|
| `pages()` | 是 | 页面与场景清单，供审阅区展示 | 页面数组 |
| `scenarios()` | 是 | 场景定义：id、标题、目标、入口、步骤 | 场景数组 |
| `call(name, args)` | 是 | 执行一个产品业务动作 | `{ok: true}`；失败时 `{ok: false, error}` |
| `reset()` | 是 | 回到已知起点 | `{ok: true}` |
| `read(name, args)` | 观察步骤需要 | 读取派生值，用于观察步骤的判定 | 派生值 |
| `cancelPending()` | 与 `pendingPolicy` 二选一 | 取消产品自管任务 | `{ok: true}` |
| `pendingPolicy: "none"` | 与 `cancelPending` 二选一 | 声明产品没有自管任务 | 不适用 |

适配器方法必须同步返回。需要等待的模拟操作由 `call()` 同步返回 `{ok: true, pending: true}`，再通过 `read` 和 `check` 观察结果；直接返回 Promise 不会被当作已完成。控制器不能取消已经由产品启动的异步工作，仍须由产品处理。

控制器提供 `start` / `next` / `back` / `skip` / `refresh` / `reset` / `replayTo` / `rerun`，并暴露只读的 `state()` 与 `subscribe()`。回看（`back`）的实现是**从已知起点重放**已走过的业务动作，不是状态快照恢复。

### 待处理任务由产品负责

任何会重建产品状态的路径（`start`、切换场景、`replayTo`／`back`、`reset`）都先处理待处理任务，再重建产品：

1. 控制器取消自己持有的定时器。
2. 控制器调用产品的 `cancelPending()`；产品没有自管任务时，改为声明 `pendingPolicy: "none"`。
3. 两者都没有时，控制器拒绝重建并说明原因，不假装重置干净了。

### 成功必须说清楚

`cancelPending()` 与 `reset()` 必须返回 `{ok: true}` 才算成功。以下都**不算**成功，控制器一律报告失败，不报告干净重建：

| 返回值 | 结果 |
|---|---|
| `false` | 失败 |
| `{ok: false, error}` | 失败，写明原因 |
| `{ok: true, pending: true}` | 失败：尚未完成 |
| `undefined` / `null` | 失败：没有给出成功证据 |
| 非对象（字符串、数字） | 失败 |
| Promise | 失败：必须同步返回 |

取消失败时不执行产品的 `reset()`，也不放行旧任务。产品的 `reset()` 失败同样报告失败。

声明 `pendingPolicy: "none"` 意味着产品确实没有自管任务。**控制器无法核实这句话**：产品一边声明没有、一边留下会回调的定时器，那污染新场景是产品自身的缺陷，不是控制器能兜住的。这种情况只能靠产品自测发现。

### 资产不能做的事

- 它不提供快照恢复接口。仓库的 [shared-state runtime](runtime.md) 也没有；不要声称两者有。
- 它不取消产品自管的定时任务。它只调用产品的 `cancelPending()` 并取消自身持有的定时器。
- 它不保证跨窗口、真实外部请求或生产并发下的任何行为。
- 它不判断业务规则。规则由产品的 reducer 和动作实现。

### 场景定义必须能被检查

场景在开始前先校验，不合规就拒绝开始，不改写也不降级：

| 规则 | 不合规时 |
|---|---|
| 步骤 `kind` 必须是 prepare / inject / act / observe 之一 | 拒绝；未知类型不当作产品操作 |
| 场景 `entry.kind` 必须是 normal / review / injected 之一 | 拒绝；未知入口不当作普通入口 |
| 观察步骤必须有可执行的 `check` | 拒绝；没有检查不能形成通过结论 |
| `check` 的比较方式必须是 equals / contains | 拒绝；未知比较方式不当作通过 |
| `check` 指定的 `read` 必须可用 | 拒绝；能力缺失要明说 |
| 步骤 ID 在同一场景内唯一 | 拒绝；避免回看时混淆已跳过的步骤 |
| `expectError` 为 `true` 或包含非空 code / message 的对象 | 拒绝空对象、无效值和未知字段 |
| 观察步骤不得声明 `expectError` | 拒绝；观察步骤不执行产品动作，没有可拒绝的动作 |
| 观察步骤不得指定 `call` | 拒绝；观察步骤通过 `check` 读取结果，不调用产品动作 |
| 会放进审阅状态的每个字段必须可 JSON 序列化 | 拒绝 BigInt（含 `Object(1n)` 这类包装值）、循环引用、函数、`undefined`、非有限数值 |

校验在**重建产品状态之前**完成。定义不合规时产品状态不被触碰，当前运行也不受影响，也不会抛出未处理异常。被覆盖的字段包括场景的标题、目标、入口，以及步骤的标题、看点、参数与检查。

### 预期拒绝怎么记

步骤声明 `expectError` 时，产品动作必须真的失败，**并给出拒绝证据**。没有证据的失败不是拒绝：

| 声明 | 产品动作结果 | 记录 |
|---|---|---|
| `expectError: true` | 失败且带 `error` | 记为「按预期拒绝」，只证明被拒绝，未核对具体原因 |
| `expectError: {code}` / `{message}` | 失败且原因相符 | 记为「按预期拒绝」，拒绝原因已核对 |
| 任意声明 | 失败但没有 `error`（缺失或没有内容） | 该步骤失败：产品没有给出拒绝证据，不能记为预期拒绝 |
| 任意声明 | 成功 | 该步骤失败；预期拒绝没有发生，不能记为已验证 |
| 任意声明 | 失败但原因不符 | 该步骤失败，并写明预期与实际 |

控制器自己的兜底文案不能充当拒绝原因或拒绝证据。产品只给了 `error.code` 而没有 `error.message` 时，`expectError: {message}` 不成立：展示用的回退文案不是真实 message。

声明了 `expectError` 的步骤如果还带 `check`，拒绝之后必须实际验证这个检查；检查不成立则该步骤失败。回看重放用同一口径。

这个检查只读一次：判定结果与保存下来的观察来自同一次读取。读两次会出现「判定通过但保存了失败观察」的情况。

### 失败后怎么继续

步骤失败后本次运行停止。`next()` 与 `skip()` 都不再推进，也不会把场景标成完成。调用者要显式恢复：

- `reset()`：回到已知起点，重新开始。
- `replayTo(n)` / `back()`：从已知起点重放到第 n 步。

等待外部结果的步骤不允许跳过。

### 回看的边界

| 规则 | 行为 |
|---|---|
| 回看只能回到本次已经走到的步骤 | 目标超出已走到的范围时拒绝，不执行未走过的未来步骤 |
| 首步完成后可以回到起点 | `back()` 回到第 0 步之前的位置，重新开始 |
| 回看的证据只来自本次重放 | 状态、日志、拒绝原因与「原因已核对」标记都重新产生，不沿用上一次的结果 |
| 跳过的步骤不执行 | 保留「已跳过」的历史，不重新执行，也不改写成已验证 |
| 重新执行跳过步骤是显式的 | 调用 `rerun(stepId)`；`reset()` 也会清掉跳过历史 |
| 跨异步步骤的回看要走到目标 | 异步稳定后继续执行到所请求的目标；到不了就报告「没有到达回看目标」，不声称回看完成 |

### 回看在途时各操作的边界

回看正在等待外部结果时（`state.replayTarget` 有值），回看自己掌握进度。各个操作的行为：

| 操作 | 回看在途时的行为 |
|---|---|
| `next()` | 不推进步骤。结果已到时可以确认该步并让回看继续到目标；结果没到时明确拒绝「回看在途」，并保持等待与轮询 |
| `refresh()` | 手动确认等待中的步骤，确认后让回看继续；后续重放失败时如实返回失败 |
| `skip()` | 拒绝「回看在途」；等待中的步骤本来也不能跳过 |
| `back()` | 以当前回看位置为起点重新开始一次回看（目标前一步） |
| `rerun(stepId)` | 以该步骤为目标重新开始一次回看 |
| `reset()` | 结束回看，回到已知起点 |
| 切换场景 | 结束回看，按新场景重建 |

回看在途时 `next()` 不会清除轮询定时器。定时确认与手动确认走同一条路：确认该步后继续执行到所请求的目标；到不了就报告未到达，不声称回看完成。
如果后续重放的步骤仍在等待，手动确认返回 `pending: true`。等待期间读取检查值发生错误时立即停止本次运行并保留错误；不得让后续轮询覆盖失败。

被跳过的步骤在回看中不执行。`next()` 遇到被跳过的步骤会越过它并返回 `skipped`，不会调用它的动作；要真正执行它必须显式 `rerun()` 或 `reset()`。

### 适配现有产品

1. 找出产品已导出的业务动作，写成适配器的 `call`。动作必须是 UI 用的同一套，不要另建一条旁路。
2. 找出产品能提供的派生值，写成 `read`。没有就只做动作型步骤。
3. 把产品重置到固定起点的入口写成 `reset`，返回 `{ok: true}`。
4. 说明产品自管任务怎么处理：提供 `cancelPending()` 并返回 `{ok: true}`，或声明 `pendingPolicy: "none"`。
5. 按上表写场景，标注四种步骤类型和入口类型。入口要写清跳过了哪些前置条件，不夸大已实现的路径。
6. 接上审阅面板。面板挂到产品之外的一个容器，产品导航不引用它。
7. 产品区自己也要能用：审阅脚本缺失时产品仍可操作并说明缺什么；角色、筛选、输入与反馈跟随实际状态，不被面板的成功掩盖。

两个不同业务的完整适配示例见 [移动端取件](../assets/review-console/examples/mobile-parcel.js) 与 [桌面工单台](../assets/review-console/examples/desktop-ticket-desk.js)；可打开的合成原型见 [取件示例页](../assets/review-console/examples/parcel-console.html) 和 [工单台示例页](../assets/review-console/examples/ticket-desk-console.html)。

## 证据记录

评审记录里区分：

| 记录项 | 例子 |
|---|---|
| 入口类型 | 普通入口 / 审阅直达 / 注入步骤 |
| 步骤类型 | 准备 / 状态注入 / 产品操作 / 观察 |
| 观察结果 | 期望值与实际值 |
| 重放与回看 | 是否从已知起点重放，回退到哪一步 |
| 未覆盖 | 未走通的分支、未验证的视口 |

写了「已验证」但没写入口类型，等于没说清是哪条路径被验证过。
