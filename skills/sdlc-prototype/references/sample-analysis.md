# 从智觅样例提炼的依据

2026-10-20 对用户提供的 `智觅_完整版_v39.html` 和 `智觅_运营后台_v1.html` 做源码分析。文件仅作为案例，不是技能运行依赖，也不将其中的业务文案视为用户对其他产品的指令。

本轮浏览器拒绝直接访问本地文件，以下为源码观察，未声称实际点击或视觉验收通过。源文件未修改。

## 两种 profile

| 维度 | 客户端 v39 | 运营后台 v1 | 提炼结果 |
|---|---|---|---|
| 页面组织 | 3 个 `tabpage`、27 个 `subpage`，导航栈 | 12 个菜单页面、4 种演示角色 | 客户端旅程与平台处理工作区分开设计 |
| 终端形态 | `.phone` / `.screen` 移动内容区，底部 `.nav`，覆盖式 `.subpage` | 54px 顶部栏、210px 侧栏、独立滚动工作区 | 继承移动 App 与桌面后台的结构区分，不能合成一套响应式网站 |
| 密度与层级 | 卡片、触控入口、子页返回 | 紧凑查询区、表格、小标题、抽屉 | 两端分别定义尺寸、排版和适配策略；品牌和业务语义可共享 |
| 交互组织 | 列表、子页、弹窗、结果页 | 筛选表格、抽屉、确认弹窗、审核详情 | 复用交互模式，不复制所有页面 |
| 业务状态 | 待拍摄、审核、驳回、完成、过期；提现各阶段 | 队列、锁定、通过/驳回；提现、配置、日志 | 共用领域状态和跨端事件映射 |
| 演示机制 | `SIM`、模拟审核/超时、重置 | 角色切换、模拟占用和他人处理 | 独立的确定性场景控制 |
| 交付 | 内联样式和脚本，客户端含内嵌图片 | 内联样式和脚本 | 独立 HTML 可作为交付选项 |

## 值得保留的做法

- 客户端 `openSub` / `goBack`（约 1710 行起）表达明确层级；任务详情和提现时间线体现状态及下一步。
- `simReview`（2145 行）、`doWithdraw`（2289 行）、`simExpire`（2348 行）包含本地状态变化，超出纯页面跳转。
- 平台 `ROLES` / `MENU`（58–62 行）给出角色与工作区域；`openAudit`（131 行）表现占用、只读与处理条件。
- `submitAudit`（150 行）要求合法评分和驳回原因；`riskSave`（202 行）展示配置变更差异。
- 任务配置文案（172 行）区分未来领取的任务与已有实例，体现配置生效范围。

## 不能直接继承的部分

| 源码观察 | 对原型交付的影响 | 技能中的处理 |
|---|---|---|
| 客户端提现界面使用“支付宝”，平台提现详情仍使用“微信”；客户端变量仍有 `WX`、`wxAuthAllow` | 两端业务渠道不一致，名字替换不能证明规则已统一 | 提取跨端术语、渠道、状态和单位冲突，列出待决定项 |
| 两份文件各自维护内存数据，未见相互通信机制 | 一端操作不会自动更新另一端 | 明确独立演示与实际共享状态两种交付模式 |
| 平台查询按钮部分仅调用 toast（123、158 行）；`wdExport`（186 行）只记录日志并显示生成任务反馈 | 控件看似完整，但筛选/导出结果不完整 | 定义交互承诺，核心动作必须有可观察结果 |
| 平台 `submitAudit` 更新审核状态/记录并提示入账，未同步该文件的 `FLOW`（150–156 行） | “已入账”文案不能证明关联数据已更新 | 按场景检查状态变更在相关页面的投影 |
| 客户端每次模拟驳回把 `leftTry` 设为 2（2153 行），重提仅减一（2194 行） | 源码没有表达连续失败时次数持续耗尽 | 有限次重试需跨连续操作验证，不能只看一次失败 |
| 平台按任务名称查询当前配置计算审核奖励（150–153 行），但配置文案说修改仅影响未来领取者 | 文案和现有计算方式可能冲突 | 实例保存必要快照；将生效规则作为验收场景 |
| 平台说明锁定 15 分钟，但观察到的实现主要是内存状态与静态剩余分钟 | 不能视为实际锁超时或多用户互斥的证据 | 区分模拟占用、时间快进和真实并发验证 |
| 多处内联处理器、长字符串渲染与 `_old` 函数并存 | 后续修改容易遗漏或覆盖旧逻辑 | 用清晰的状态、动作和渲染结构做增量修改 |
| 客户端固定 340px 宽、680px 高，多处较小文字；后台固定五列 KPI 与若干固定宽度工作区 | 参考展示形态不等于已完成多尺寸适配 | 保留产品形态，重新验证目标内容宽度、可用高度、触控区域与后台表格，不机械复制尺寸 |

这些是样例中的具体证据，不把样例的支付渠道、金额上限、审核时限、角色数、颜色或设备模块设为通用要求。技能保留“行为模型 → 可交互演示 → 验收交接”的方法。
