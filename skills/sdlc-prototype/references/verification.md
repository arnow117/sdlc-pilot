# 联动验证

三种证据分开记录：状态测试、实际 UI 操作、视觉检查。任何一种都不能代替另两种。

## 状态测试

从已知 fixture 调用 UI 使用的同一套业务 action。选择会造成真实误判的边界，而不是复制实现表达式作为断言：

| 类别 | 需要观察的结果 |
|---|---|
| 成功路径 | 主实体、关联记录、可用数量和汇总同时满足期望 |
| 非法状态/权限 | 整个状态不变，返回可理解的拒绝原因 |
| 重复操作 | 不重复发放、扣减、占用或追加记录 |
| 连续操作 | 提交、拒绝、重试、成功之后状态仍正确 |
| 多对象 | 对象 A 的操作不污染 B；身份切换后按数据范围展示 |
| 配置/历史 | 若有快照语义，旧对象不被新配置重算 |
| 重置/延迟 | 重置后旧定时结果不能覆盖新状态 |

对库存、名额、余额等共享资源，写下领域不变量，并在动作完成后检查。状态校验失败不得发布部分结果。测试失败要核对规则与实现，不应通过放宽断言来绕过矛盾。

## UI 联动

从实际用户入口操作，不直接注入目标状态再截结果图。典型双端路径：

1. 读者端发起动作，记录对象标识和数量。
2. 切到后台，确认同一对象及相关计数。
3. 后台执行处理，再切回读者端。
4. 检查列表、详情、标签、下一步操作和汇总一致。
5. 覆盖一个失败/取消分支，确认没有伪成功或错误副作用。

同时检查查询真的过滤、表单错误能修正、取消能返回、弹窗可关闭。只出现 toast 不算联动证据。若 UI 工具受限，记录实际完成的部分，不把状态测试改称点击测试。

## 各端形态与适配

- 移动 App：在目标手机宽度和至少一种较短高度检查底部导航、最后一项、主操作和安全区域；桌面预览仍保持移动结构。详情返回后检查查询、选择对象和列表位置，弹层不能跑到预览容器之外。
- 响应式 Web：分别检查目标断点下的导航、列数和内容重排；不以缩放文字替代布局。
- 桌面后台：在主要桌面宽度检查侧栏、过滤区、表格与编辑弹层；窄屏按既定支持范围检查菜单展开、局部滚动和操作可达性。

记录的视口应对应各端实际约定。测试“页面未溢出”不能证明其导航形态符合参考，也不能证明未覆盖的移动办公流程可用。

## 交付物一致性

测试应覆盖打包进去的同一份领域源码。若测试模块与单文件 HTML 通过构建合并，检查最终文件确实由当前源码生成，没有独立复制的第二份业务逻辑。

离线交付检查外部脚本、字体、图片和 API 依赖；使用已有许可浏览器在实际入口验证。浏览器拒绝某个目标时，不以换通道等方式绕过限制。

## 三种入口分别验证

同一条旅程有三种到达方式，证据强度不同，不能合并成一个「已验证」。

| 入口 | 怎么走 | 成立的条件 | 记录为 |
|---|---|---|---|
| 普通入口 | 从产品正常导航出发 | 已说明并在约定环境建立前置条件；注入逐步标明 | 该入口的（局部／模拟）旅程证据 |
| 审阅直达 | 直接跳到某一页或某一步 | 明确写下跳过了哪些前置条件 | 局部行为证据 |
| 注入步骤 | 由演示控制注入状态或外部结果 | 明确写下注入了什么 | 模拟证据 |

验证口径：

- 普通入口要单独走一遍。它是唯一能证明「用户能走通」的口径。
- 审阅直达用于检查单页或单步行为。它不能证明前置条件成立，也不能代替普通入口。
- 注入步骤用于复现外部结果。它证明的是模拟链路可复现，不是真实外部行为。
- 同一场景的结果不一致时，分别记录入口、触发条件和差异，并对照已确认的产品规则；普通入口的观察反映其实际路径，不自动决定哪种行为符合产品意图。

写记录时把两件事分开：

- 用户操作是否从普通入口实际走过。走过就记为该入口的局部或模拟旅程证据，并写明这次覆盖到哪一步。
- 外部结果是否由演示注入。注入的逐步写明，不写「已发生真实外部行为」。

只有外部结果被注入，不等于「未从普通入口走通」；反过来，只走过审阅直达，也不能写成普通入口已走通。缺失的一方不补到另一方头上。

三类入口与四种步骤类型（准备、状态注入、产品操作、观察）的完整定义见 [review-console.md](review-console.md)。

## 交付依赖按旅程检查

对本次每条核心旅程，说明交付物跑起来需要什么，并实际走一遍。

| 检查项 | 问什么 | 结论写法 |
|---|---|---|
| 能否启动 | 打开文件能否直接运行 | 可启动 / 需要特定环境 |
| 相邻文件 | 是否依赖同目录其他文件 | 列出依赖的文件名 |
| 外链资源 | 是否引用 CDN、远程字体、在线 API | 列出必需与可选资源；离线旅程不能依赖不可用的远程资源，可选外链需验证回退或说明其不影响约定旅程 |
| 运行方式 | 单文件双击、静态服务还是工程命令 | 写明实际使用的方式 |

结论分三段写：

1. **能否启动**：在约定环境下实际打开的结果。环境不满足时写明缺什么，不用「应该可以」。
2. **核心旅程是否可完成**：按普通入口实际走一遍的结果，包含中途失败的反馈与回退。
3. **资源失败时**：资源加载失败时用户看到什么，是否有降级或明确提示。

只有用户要求离线时，才按离线承诺验收。未约定离线时，如实列出实际用到的外链即可，不必为满足离线而改造交付物。真实外部请求永远不由模拟证据冒充——页面显示「到账」不等于发生过真实外部操作。

## 记录格式

记录版本或内容 hash、测试命令及结果、UI 实际步骤与观察、视口及截图、未验证项。按相关输入变化补测，测试通过后不为追求次数重复执行。
