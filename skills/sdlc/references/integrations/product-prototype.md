# sdlc-prototype — 包内产品原型适配

`sdlc-prototype` 是随 sdlc-pilot 分发的可交互原型制作方法。它可以独立使用，也可以由产品或规格阶段按需使用；已明确
计划的原型迭代由 plan 消费、评估和记录，并由 build 更新。它不创建生命周期、角色、状态字段、manifest 或第二份产品/工程
上下文。主 Agent 拥有编排和生命周期；当前 stage 保持既有边界与输出，原型只是其中的方法。本参考是 SDLC 的原型选择策略和
接口唯一权威来源；当前 `product_context_ref` 拥有产品意图和 confirmed 规则。

## 1. 召回时机与选择策略

本节是 SDLC 侧原型选择策略的唯一权威来源。其他 router、stage 和角色卡只提示早期召回并链接本节，不复制另一套判断矩阵。

### 1.1 何时召回

每次产品设计或产品规格开始时，先读包内 [`sdlc-prototype`](../../../sdlc-prototype/SKILL.md) 的技能入口和本节，再展开规格、
提出产品问题或形成 stage brief。召回不依赖用户点名该技能，也不推迟到设计结束后判断：

- orchestrated mode：主 Agent 在形成 product-design 或 spec 的 stage brief 前完成判断，写入判断结果与依据；需要创建或
  更新原型时，还须在 brief 的既有字段给出有界可写目录和范围。
- standalone mode：直接进入产品设计或规格的调用方自行完成判断；需要制作或更新时，使用项目约定目录。

初次判断依据现有事实；信息不足时记录未知项，后续新事实改变判断时按第 1.4 节处理。

只有产品设计与产品规格阶段做这次召回。plan、build 等下游阶段消费已确认的原型输入，不重新判断原型适用性。不要求所有任务
都进入完整 SDLC。

### 1.2 三种选择

判断只落在下列三种结果之一：

| 结果 | 适用条件 |
|---|---|
| 使用原型方法 | 用户明确要求制作、迭代或分析，或受影响的交互需要进一步设计；按需新建、增量修改或仅用 `inspect` 分析 |
| 复用已确认足够的基线 | 已有 confirmed 原型或设计覆盖本次受影响旅程，且本次不改其行为、角色权限、状态反馈或跨端联动 |
| 说明依据后跳过 | 用户明确要求跳过，或经核对本次没有需要设计的用户可见交互 |

按顺序判断：用户明确要求跳过时记录并跳过；明确要求制作、迭代或分析原型时按其指定形式使用。否则，只有 confirmed 基线
覆盖本次受影响旅程，且本次不改变所覆盖的行为、角色权限、状态反馈或跨端联动，才复用该基线。没有足够基线时，经核对确实没有
需要设计的用户可见交互，可以说明依据后跳过；其余情况使用原型方法。纯内部后端工作、不改变行为或验收的文案和样式调整是
可能跳过的例子，不能仅凭“后端”“文案”或“没有新页面”判断。

以下两点不能作为跳过依据：

- 没有新页面不等于没有实质变化。真实角色、控制台交互、状态反馈、语音或设备行为、跨端旅程的实质变化都算实质变化，页面
  数量不变也要重新判断。
- 未知不等于已有足够基线。没有 confirmed 的原型或设计、覆盖范围说不清或证据不足时，不得按“复用已确认足够的基线”处理；
  如不能确定无需设计交互，使用原型方法或先补齐判断依据。

### 1.3 制作范围与确认边界

选择使用原型方法时，以最小受影响旅程有界制作或评审，不重做未受影响的范围。不强制每个需求都产出 HTML：交付形态按
本次受影响范围决定，可以是页面、片段、状态流或既有原型的增量修改。需要通过实际操作评审角色、流程、状态或跨端反馈等体验
决定时，提供最小可操作原型；只需分析已有材料或用户明确只要求分析时，可按 `inspect` 模式给出方案，并记录不制作交互原型的依据。

是否需要用户决定遵循阶段协议的[判断边界](../stage-agent-protocol.md#judgment-boundary)。已确认或已明确委托的选择直接沿用；
普通布局和示例值可按合理默认推进，不必逐项询问，未确认的决定仍在产品上下文标注为候选。

原型里未决定的规则仍是候选，不因被画出来就变成 confirmed。产品确认与模拟检查分开：原型能证明可见行为和演示路径，真实
产品或设备行为由正式实现与验证阶段重新证明，不因原型通过而省略。

### 1.4 记录方式

判断结果和依据写进既有的产品上下文或 stage brief，不新增 state 字段，也不强制另起一份决策文件。编排模式下，执行者以 brief
为起点；发现新事实可能改变选择时反馈主 Agent，按阶段协议更新 brief。需要创建或更新原型但缺少有界写权时，暂停受影响的写入，
报告主 Agent 补齐完整 brief；不得自行扩大写域或静默跳过，已授权且不依赖该缺口的工作继续。

### 1.5 包内发现

方法和所需 references、共享状态 assets 均位于包内 [`sdlc-prototype`](../../../sdlc-prototype/SKILL.md)。当前宿主尚未发现本地新技能时，不能声称
`/sdlc-prototype` 已可调用；安装或刷新宿主索引后，插件身份为 `sdlc-pilot:sdlc-prototype`，本地发现名称为
`sdlc-prototype`。包内链接缺失是分发包缺口，不发现、安装或恢复外部旧 `product-prototype` 技能。

## 2. 既有 brief 和结果中的接口

不新增 schema、manifest 或状态记录。当前 stage 的既有 brief（见
[stage-agent-protocol.md](../stage-agent-protocol.md)）明确权威产品上下文和判断依据；需要原型时按适用情况补充：

- 场景范围及已有 `SCN-*`、`RULE-*` 等标识，现有原型的路径和版本；
- 目标终端形态、品牌或设计系统、演示/同步范围；
- 项目约定的原型产物目录、可写边界、完成条件和验收方式。

需要创建或更新原型时，brief 给出该产物的有界可写目录与范围，使执行阶段不因缺少写权而跳过原型。

沿用既有 stage result/交接格式返回：产物路径及版本、hash 或 commit；场景到原型锚点的映射；实际执行的证据和限制；
候选决定与开放问题；以及可供工程规划评估的组件、token、fixture 或代码复用候选。原型不把观察或演示假设升级为
confirmed，也不直接修改 `.sdlc-v1/state.json` 或请求新的生命周期操作。

产品或规格阶段展示候选时，主 Agent 给出可打开的入口、版本、可走通的核心旅程、需要用户尝试的具体动作、实际检查范围、
模拟部分和仍待决定的选择。反馈面向可见行为，而不是泛问是否满意。确认、明确委托和开放项仍记录在现有产品上下文：反馈影响行为时，
更新受影响原型版本、场景映射和决定的替代关系，并让 plan 更新受影响设计与计划验证。原型存在、点击检查或未收到反馈不自动确认
产品意图，也不构成生产实现、validation、review 或 release 证据。

## 3. 阶段边界与证据归属

| 阶段 | 使用方式与写入边界 |
|---|---|
| product-design / spec | 按本参考选择使用原型方法、复用或跳过。需要创建或更新有界 demo 时，编排模式使用 brief 明确命名的项目约定目录，独立调用使用项目约定目录；目录在 `.sdlc-v1` 外，且不改生产代码。产品上下文保留产品意图、confirmed 来源、场景映射、原型 baseline 及产品阶段实际证据/限制。阶段 Agent 不自行 fan out。 |
| plan | 读取已确认的原型输入，决定组件、token、fixture 或代码是否复用，并只将适用的 confirmed 场景映射到生产验收与计划验证；演示假设和开放替代项仍是候选。当前有效方案明确记录有界原型迭代的资产范围，由 build 更新。工程上下文记录复用/实现决定和引用的版本；引用原始产物，不复制报告。 |
| build | 只按计划中明确的生产实现和/或原型资产范围工作；原型不是第二套实现或状态来源。`.sdlc-v1` 外受跟踪原型资产变化需要新的业务验证 baseline。实现遵循既有仓库角色路由和主 Agent 派工，stage Agent 不自行 fan out。需要调整产品行为时回到既有产品/规格流程。 |
| validate / review | 只读当前实现和已有原型输入。原型点击或模拟结果不能证明生产持久化、并发、认证/授权或其他正式实现行为；正式实现重新验证相关语义场景。`.sdlc-v1` 外的受跟踪产物（包括原型资产）变更必须走既有 build/validate 路径并建立新的验证基线，不能因标为 demo 而沿用旧结论。只有产品/工程上下文的语义变化，才按[既有证据适用规则](../stage-agent-protocol.md#context-prose-and-evidence-applicability)判断覆盖：能复用时记录理由，否则走既有 plan/build/validate 路径。发现修正需求时按既有 plan/build 流程返回。 |

demo 需要更复杂运行时行为时，在允许的原型产物内使用可替换的模块与 mock adapter；这不改变生命周期、状态归属或生产实现边界。

产品确认时，以原型版本和覆盖场景建立 baseline。受影响旅程变化，或已有授权的视觉/demo 展示工作更新原型时，只刷新相关范围并记录适用版本与覆盖场景；不把原型与生产 UI 维护成永久的全量双份界面。Feature 的实现选择、正式验证与 review 证据属于工程上下文，原始原型产物只由该上下文引用。

直接调用 `sdlc-prototype` 创建、分析或迭代与当前 tracked Requirement/Feature/Task 无关的原型时，不初始化 state，也不启动无关生命周期。已跟踪工作直接调用时仍读取当前 stage、brief 和产物目录，并遵守本表的写入边界。
