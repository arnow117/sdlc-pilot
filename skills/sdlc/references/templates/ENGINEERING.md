**输入**：本文档中的“架构设计”和“实施计划”
**前置条件**：实施计划（必需）、产品规格（用户故事必需）

**测试**：当仓库约定、规格、计划或既有工作流要求测试时，测试是必需的。仅在该策略适用时采用测试先行顺序；否则纳入与改动相称的验证工作。

**组织方式**：任务按可独立交付价值和共享写入边界分组；紧密相关的用户故事可由一个完整 Task 连续实现和测试。优先安排最小可运行的核心用户旅程；只有该旅程实际依赖的准备和基础工作应先于它，其他基础或横切工作按其真实依赖关系安排。

#### 格式：`[ID] [P?] [Story] 描述`

- **[P]**：候选并行任务；实际并行资格由[阶段代理协议](https://github.com/arnow117/sdlc-pilot/blob/71b0da74ff06d771db23203d13174939aef30f19/skills/sdlc/references/stage-agent-protocol.md)判断，而非仅由不同文件或无依赖决定
- **[Story]**：任务所属用户故事（例如 US1、US2、US3）
- 在描述中包含确切文件路径
- 每项任务必须产生单一可验证结果。当拆分会使结果不可验证或制造人为协调时，一项任务可触及多个紧密关联文件。
- 添加“覆盖：REQ-xxx；计划：<组件/阶段>”以保留可追溯性。

#### 路径约定

- **单项目**：仓库根目录的 `src/`、`tests/`
- **Web 应用**：`backend/src/`、`frontend/src/`
- **移动端**：`api/src/`、`ios/src/` 或 `android/src/`
- 以下路径假定为单项目；按实施计划中的实际结构调整

#### 依赖与执行顺序

##### 阶段依赖

- **准备（阶段 1）**：无依赖——可立即开始
- **基础（阶段 2）**：依赖首个故事所需的准备完成——只阻塞依赖这些基础的故事
- **用户故事（阶段 3+）**：各自依赖已声明的最小前置条件
  - 满足自身依赖后可按协议并行推进（资源允许时）
  - 或按优先级顺序推进（P1 → P2 → P3）
- **收尾（最终阶段）**：依赖所有预期用户故事完成

##### 并行机会

- 所有标记 [P] 的准备任务可作为并行候选
- 所有标记 [P] 的基础任务可作为并行候选（在阶段 2 内）
- 基础阶段完成后，所有用户故事可作为并行候选（团队容量允许时）
- 一个用户故事中所有标记 [P] 的测试可作为并行候选
- 故事内标记 [P] 的模型任务可作为并行候选

#### 执行策略

##### MVP 优先（仅用户故事 1）

1. 完成用户故事 1 实际需要的阶段 1：准备
2. 完成用户故事 1 实际需要的阶段 2：基础
3. 完成阶段 3：用户故事 1
4. **检查并验证增量：**独立测试用户故事 1；这用于检查当前增量，不表示整个 Task 或 Feature 已完成
5. 如已达到可查看的稳定增量，按阶段协议报告实际入口、命令、版本、范围和缺口，并继续同一 Task

##### 增量交付

1. 完成用户故事 1 所需的准备 + 基础 → 最小旅程就绪
2. 加入用户故事 1 → 独立测试 → 可按协议展示真实增量；原授权仍覆盖后续工作时继续同一 Task
3. 加入用户故事 2 → 独立测试 → 仅在存在独立交付边界时再拆分或交接
4. 加入用户故事 3 → 独立测试 → 完整 Task 通过必要检查后才请求 done
