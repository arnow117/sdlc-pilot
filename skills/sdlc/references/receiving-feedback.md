# receiving-feedback — 接收意见并修复的纪律(蒸馏自 superpowers:receiving-code-review)

> 共享纪律，供 [`stage-agent-protocol.md`](stage-agent-protocol.md#4-results-transitions-and-correction) 和
> [`sdlc-review`](../../sdlc-review/SKILL.md) 在返修或处理意见时引用。
> 治的病:**agent 一被指出问题就疯狂乱改 / 表演式同意 / 盲目照单全收**。
> 核心原则:**先核实再改、先问再假设、技术正确 > 社交舒适。意见是待评估的建议,不是必须执行的命令。**

## 响应模式(每条意见都走一遍)

```
READ        完整读完,先别反应
UNDERSTAND  用自己的话复述这条要求(说不清就问)
VERIFY      对照代码库现实核实——这条对本仓成立吗?
EVALUATE    技术上对吗?会破坏现有功能吗?当前实现是不是有它的理由?
RESPOND     技术性确认,或有理由地反驳
IMPLEMENT   按可独立验证的修改逐项实施
```

## 三条防乱改铁律

1. **改前先核实,不盲改**:任何 finding 先对照代码库确认它**真的成立 + 对本仓正确**,再动手。看着对 ≠ 真的对。
2. **不清楚时暂停依赖该决策的工作**:集中澄清后再修该项；已理解且不依赖未决点的工作可以继续。不要根据对同一项的部分理解边问边改。
3. **改动逐项验证、不引入回归**:可以批量阅读、核实和回应，但每个可独立的修改都要用相关验证结束。顺序:阻塞性(break/安全)→ 简单(typo/import)→ 复杂(重构/逻辑)。

## 该反驳就反驳(意见也会错)

遇到以下情况**用技术理由反驳,不照单全收**(也不防御性顶撞):
- 会破坏现有功能 / reviewer 缺全貌 / 技术上对本栈不对 / 有兼容性·legacy 理由 / 与已定架构决策冲突。
- **YAGNI grep**:意见让"做个正经的 X"→ 先 grep 它是否真被调用;**没人用就提议删,别顺手加**没要求的东西。
- 自己反驳错了 → 一句话事实纠正即可:"核实了你对,我之前理解错在 X,改。"——不长篇道歉、不辩解。

## 禁止 / 改用

| ❌ 禁止 | ✅ 改用 |
|---|---|
| "你说得对!""好的我改"(表演式同意) | 复述技术要求,或直接动手 |
| 改前不核实就实现 | 先 VERIFY 对照代码库 |
| 批量阅读后无差别地批量改 | 先归类，再逐项处理并用相关检查验证 |
| 改对了写"谢谢指出""好眼力" | 直接说"已修:<改了什么>",代码本身证明你听进去了 |

## 批量意见的完整性

先批量阅读、核实、分类和回应，再对已决的修改逐项实施。对涉及多个位置、存在争议，或会改变验收条件、Task 或测试的批注，在当前上下文的反馈部分对每个可执行意见记录处理结果、原因和证据，必要时指明受影响的验收条件、Task 或测试。

- 保留已有 ID；没有 ID 时用简洁的意见描述，不强制生成 ID。一两条简单意见可以直接回应，不建立账本、文件或表格。
- 明确区分：已接纳但尚未实施、已修复并验证、有证据地拒绝、非阻塞延后、等待用户决定。这些是文字处理结果，不是新的状态字段或状态结构。
- 同一根因的重复批注可合并，但需保留各条意见与合并结果的对应。可复用仍匹配的验证证据，不为每条重复运行相同检查。
- 实质产品变更写入产品上下文；实质的当前有效方案、接口或策略变更仍按当前有效方案和完整 `supersedes` brief 处理。意见不自动被采纳；保留改前核实和必需验证。

## 在 SDLC 内的接入点

- **stage-agent-protocol**:批量评审或用户意见的核实和处理结果按本纪律记录。
- **sdlc-review**:处理评审意见时，先核实它对本仓的技术正确性；需要修改实现时返回 build，由实现阶段负责修复；拿不准时请求澄清。
