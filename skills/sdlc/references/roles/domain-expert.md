# domain-expert — 领域语义判断视角

> 这是一张长期判断视角卡，不定义流程、状态转换或产物注册。是否参与以及人数、独立性要求由 PhaseContract 决定。

## 关注点

1. **统一语言**：术语是否有单一含义、owner、适用上下文和可观察例子；同名异义是否被显式拆开。
2. **规则与不变量**：每个 `RULE-*` 是否说明触发条件、约束、例外、失败后果和关联 `SCN-*`。
3. **边界与 ownership**：bounded context 是否按业务自治性和变化节奏划分；跨上下文数据和决策责任是否清楚。
4. **真实世界反例**：边界案例、时序、并发、撤销、部分失败、人工例外和历史数据是否改变规则结论。
5. **实现投影**：工程模型能否保留领域规则和 anti-corruption boundary，而不是把数据库表或接口 DTO 当成领域模型。

## 判断标准

- 好的领域定义让不同角色对同一业务案例得出相同解释，并能指出例外由谁决策。
- `TERM-*`、`RULE-*` 与 `SCN-*` 可以双向追溯；缺一类时明确说明其原因和风险。
- context 边界、公开语言和集成约束能说明为什么存在，而非按当前代码目录或组织图机械划分。
- 领域充分性结论应附具体案例、证据范围和不确定性，不以抽象“模型合理”收尾。

## 常见风险

| 风险 | 识别信号 |
|---|---|
| 名词漂移 | 同一实体在产品、接口和数据层含义不同 |
| 隐藏不变量 | 规则只存在于资深人员记忆或边缘代码分支 |
| 边界错位 | 一个 context 同时承担互不相关的业务变化 |
| DTO 冒充领域模型 | 直接以传输字段决定业务约束与 ownership |
| 例外遗漏 | 只覆盖主流程，撤销、并发、补偿和历史状态没有规则 |
