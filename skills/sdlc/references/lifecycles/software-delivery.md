# Software delivery lifecycle

> distilled-from: [Zts0hg/codexspec](https://github.com/Zts0hg/codexspec/tree/d76d358a9f79a9b131bb2eccb85670e5d81b7dca/templates/docs)

软件交付把 ready Requirement 转为 `.sdlc-v1/context/<feature-id>.engineering.md`、代码和可验证的 Git commit。按改动风险选择方法，不要求小改动复制完整架构文档。

## 0. 执行纪律

以下是规划、实现和评审的阶段方法。派工、子 Agent 层级、验收、检查点和 transition 规则唯一见
[`stage-agent-protocol.md`](../stage-agent-protocol.md)；本文件不重复定义它们：

本节改编自 [multica-ai/andrej-karpathy-skills 的 `karpathy-guidelines`（MIT）](https://github.com/multica-ai/andrej-karpathy-skills)，保持自包含，不要求运行时安装外部 Skill。

- 在开始会影响实现或验收的工作前，写明关键假设。涉及公共接口、持久化数据、不可逆外部行为或验收条件的歧义必须先确认；低风险歧义说明采用的默认值后继续。
- 选择能满足当前验收条件的最简单方案；不为未明确要求的未来场景新增抽象、配置或扩展点。
- 每项代码改动必须能对应当前 Task 或验收条件。不要顺带重构、格式化或清理无关代码；只删除本次改动产生的无用代码。
- 完成必须可验证：逐条满足 Task 完成条件和产品验收条件，并记录实际检查命令及结果。无法执行首选检查时，记录原因与最接近的替代验证。

## 1. Engineering specification

研发上下文的一个当前有效方案应把当前产品验收条件映射到实现：

- 当前代码入口、数据流和约束；
- 拟修改的模块与接口；
- 数据结构、兼容性和部署影响；
- 每条当前验收条件对应的设计或契约、Task 和计划验证；新 Feature 在 `add-task` 前可先写计划 Task，登记后替换为实际 Task ID；更新 Feature 时引用既有 Task；
- 明确不改的区域、关键假设和低风险默认值。

有实质取舍时，可以增加轻量设计决定：问题与约束、选择、重要替代方案及取舍、适用的 Requirement/验收条件，以及何时需要重新评估。重要接口或决策可使用 `ARCH-*`、`API-*`、`DATA-*` 标识，但不要求简单改动增加 ID 或表格。

简单场景可以用一行“验收条件 → 设计/契约 → Task → 计划检查”说明关联；跨客户端、API、兼容性或恢复行为需要分别说明时，使用紧凑映射。架构说明和实现顺序可以分节描述，但都属于同一个当前有效方案，不能形成第二份权威计划。验证的实际结果留在现有验证/证据部分，评审只引用这些结果和缺口。

小 Feature 只压缩与当前范围无关或已经由引用覆盖的细节：仍需在同一当前有效方案中说明实际验收条件、最小设计、Task 边界与计划验证。不要以“简写”为由另建替代模板、固定篇幅、重复交接或省略必要接口、数据保护、失败边界和验证。可参考[小项目上下文示例](../../../../examples/small-project-context.md)的填写粒度；复杂度或风险上升时在现有章节展开。

新建或实质更新的工程上下文按 [ENGINEERING.md](../templates/ENGINEERING.md) 保留 design、详细 plan 与详细 tasks 的源顺序；
设计固定核心始终保留，条件可选设计仅在适用时出现。实际验证和评审记录独立于当前有效方案；它不是独立 ADR 库或进度记录。
产品侧的决定来源仍以[产品决策来源与变更](product-design.md#7-产品决策来源与变更)为准。

## 2. 架构设计

跨多个 surface、改变公共接口或引入新依赖时，检查：

- 模块边界、依赖方向和所有权是否清楚；
- 失败是否被隔离，是否需要超时、重试、幂等和降级；
- 数据一致性、并发和版本兼容如何处理；
- 方案是否可渐进部署、观测和回滚；
- 是否存在更小且足够的方案。

高风险持久化格式、跨机器协议、不可逆外部行为和公共 API 兼容性决策，可以增加一次独立的对抗性复核。普通功能、重构和局部实现不需要。

### 图示辅助对齐

这是产品、工程上下文共用的表达约定。新建或实质更新复杂流程时，按下表选择能解释当前分歧的图；
默认先画最小范围的一张，再按阅读需要补充。已有图或有序短句能清楚表达时直接复用或省略，简单线性逻辑无需图。
保持模板原有章节顺序和必填/条件可选区分，不新增独立图册、审批步骤或“每份文档必须有图”的完成条件。

| 需要对齐的问题 | 优先表达 | 放入现有章节 |
|---|---|---|
| 多角色操作、业务分支、失败后的恢复入口 | 流程图（`flowchart`） | PRODUCT 的对应用户故事；图仍只描述外部行为 |
| 状态转换的触发条件、允许与禁止的变化 | 状态图（`stateDiagram-v2`） | PRODUCT 的用户故事；实现层转换机制放 ENGINEERING 的时序与数据流 |
| 跨组件调用顺序、异步回调、重试、超时或并发竞争 | 时序图（`sequenceDiagram`） | ENGINEERING 的时序与数据流 |
| 组件职责、依赖方向、数据所有权或信任边界 | 组件关系图（`flowchart`） | ENGINEERING 的架构与组件 |
| 多实体关系和基数不易从字段说明读出 | 实体关系图（`erDiagram`） | ENGINEERING 的数据模型 / 关键实体 |

图示优先用 Markdown 内嵌 Mermaid，源文本随所属上下文进入 Git，便于人审阅和 Agent 修改；使用常见语法，
不为画图引入强制依赖。GitHub 的代码块写法见[官方说明](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams)，
时序与状态语义分别见 [Mermaid 时序图](https://mermaid.js.org/syntax/sequenceDiagram.html)和[状态图](https://mermaid.js.org/syntax/stateDiagram.html)。

每张图聚焦一个问题，旁边用短句说明范围、关联的现有场景/REQ/接口，以及仍需决定的分歧；无需新增编号体系或固定字段。
参与者、消息、状态与正文使用同一术语；影响当前判断的拒绝、失败、恢复或竞争结果不能被成功路径掩盖。
图不重写接口字段、验收条件或测试证据，省略的细节引用其权威章节。假设和开放项保持明确标注，不能因画进图就变成已确认决定。

在已有 spec/plan 对齐环节，先展示与当前决定有关的图和短说明，再沿图走一遍代表性场景及相关失败/边界分支，
对照正文检查起点、条件、责任方和结果；集中讨论仍未确定的分支。按既有产品确认与工程授权规则记录结论，不增加逐图确认。
Build 中已获授权的设计变化由上下文的负责写入者同步图和正文；产品行为变化仍回产品侧确认。
Review 对照当前方案、实现和已有验证证据检查一致性，发现矛盾返回负责阶段修正，不直接重画方案来消除差异。
有现成预览能力时检查渲染与可读性；不能渲染时保留源文本并提供等价的有序说明，如实说明未预览。
渲染通过只说明表达可读，不证明实现或并发语义正确。

PROJECT 只索引已验证的长期架构图来源；TASK 的 `context_refs` 和 CHECKPOINT 的“必要引用”指向相应上下文章节，
避免复制图。图表达业务或设计关系，生命周期进度仍唯一来自 `state.json`；历史文档无需批量补图。

## 3. 领域映射

业务规则复杂时，将产品术语映射到代码职责：

- 聚合或一致性边界；
- 命令、查询、事件和状态变化；
- 仓储、外部服务与领域逻辑的分工；
- API DTO、领域对象和持久化对象之间的转换。

避免只因采用某个模式而增加抽象；模型应减少规则分散和状态不一致。

## 4. 可靠性设计

涉及外部系统、长任务、数据处理或高可用要求时，说明：

- timeout、retry、backoff、circuit breaking；
- 幂等键、去重和重复投递；
- 容量、限流、背压和资源上限；
- 日志、指标、追踪和告警；
- 数据修复、降级、恢复与演练。

每项应对应产品质量要求和具体测试或演练方式。

## 5. 规划

把设计拆成可独立验证的 Task：

1. 每个 Task 有明确代码范围、完成条件和测试方式。
2. 用 Task ID 表达依赖；保持依赖图无环。
3. 优先按纵向可运行增量拆分，避免长时间只有基础设施而无可观察行为。
4. 记录接口与依赖；是否允许并行、如何隔离和怎样集成由主 Agent 按 canonical protocol 判断。
5. 小改动可以只有一个 Task。

## 6. 实现（TDD）

默认循环：

1. 选择一个依赖已满足的 Task。
2. 写最小失败测试并确认失败原因。
3. 实现使测试通过的最小改动。
4. 重构并重新运行相关检查。
5. 更新研发上下文中的长期工程决策。
6. 将 Task 标记为 done。

文档、纯配置、生成文件或无法先测试的机械改动，可以先实施再运行最接近的静态或集成检查，但必须记录验证方式。

## 7. 调试

意外失败时：收集事实 → 提出一个可证伪假设 → 做最小实验 → 根据结果保留或否定假设。每轮只改变一个主要变量。定位到产品规则缺口时停止实现，回到产品上下文确认。

## 8. 验证

根据 project surface map 和 diff 选择单元测试、类型检查、构建、端到端、契约、视觉或评估检查。逐条核对产品验收条件，记录实际命令和结果。

通过结果必须绑定到业务代码工作树干净时的当前 Git commit。之后可以只修改或提交 `.sdlc-v1/**`；该目录之外的代码变化需要重新验证。
`.sdlc-v1` 上下文文字的语义变化是否仍可复用既有证据，按
[stage-agent-protocol 的 context-prose-and-evidence-applicability](../stage-agent-protocol.md#context-prose-and-evidence-applicability)
由主 Agent 判断；它不是 CLI 自动推断的状态变化。

## 9. 评审

按 diff 选择角色，独立检查正确性、回归、架构、数据、安全、体验和可维护性。每个问题给出文件位置、影响、修复建议和判断依据。

必须修复项清零且修改重新验证后，才能批准 validation commit。后续仅含 `.sdlc-v1/**` 的证据提交不使验证失效。

## 10. 发布准备

确认构建产物、配置、数据变化、部署顺序、smoke、观测和回滚方案。实际发布由 `sdlc-ship` 执行；发布实现版本始终是 validation commit，后续仅含 `.sdlc-v1/**` 的提交不替换它。

## 11. Global usage-document, story, and parameter contract

面向使用者的当前操作说明只维护在目标项目的一个全局 usage 入口。它以稳定的全局
story/scenario ID 导航到既有产品故事和验收条件，而不是复制规格；每个受影响故事应说明
actor、当前入口、前置的身份/权限/环境、参数由哪个 owner 或既有 schema/指南提供、默认
范围、正常步骤和可观察业务结果、失败/撤权/未知结果的恢复，以及当前支持范围。

规划阶段（`plan`）先判断文档、故事和参数来源是否受影响；内部实现改动可记录为不适用及理由，但不得
虚构用户故事。Build 同步更新该入口和它所链接的详细操作说明。参数的权威仍在受控 schema、
部署配置或详细操作指南；usage 文档只引用来源，绝不记录 secret。

Validate 对每个受影响的使用路径选择代表性目标环境，按当前文档和来源参数实际操作，并在
既有工程/发布证据中绑定 candidate、环境、身份/权限引用、原始命令或 UI 步骤、业务结果和
必要的语义截图。不要为每条 Requirement 新建存证包。测试存在、截图、doccheck 或合成运行
都不等于真实可用：未运行和失败是执行结果；合成、reference、staging、真实目标及其未覆盖范围
是环境/数据范围，二者必须分别明确标识。Review 核对
文档 → story → 参数 → 实际使用结果的一致性；Ship 核对所选目标版本的可用条件，不用本地
synthetic 结果替代 live、部署或真人试用要求。

Validate 和 Review 保持对实现与 usage 文档的只读纪律：若实际操作发现指南或参数来源错误，
返回 Build 更新指南并重新运行受影响验证；不要以验证或评审阶段直接改写指南来规避
validation-commit 绑定。

能力废弃或失效时，及时改正当前指南并保留历史诊断和原有验收条件；不得因文档检查通过而推进
lifecycle。全局 usage 入口和实际使用验证是已有验收/发布证据的导航与联动，不降低其原有
条件。
