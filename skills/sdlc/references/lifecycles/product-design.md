# Product design lifecycle

> distilled-from: [Zts0hg/codexspec](https://github.com/Zts0hg/codexspec/tree/d76d358a9f79a9b131bb2eccb85670e5d81b7dca/templates/docs)

产品设计把原始请求收敛为 `.sdlc-v1/context/<requirement-id>.product.md`。新建或实质更新的上下文按
[PRODUCT.md](../templates/PRODUCT.md) 保留源 requirements 与详细 spec 的章节和必填/条件可选区分；简单需求可以简写适用内容。
简写只压缩重复说明：仍按原顺序覆盖已确认的用户结果、范围和验收场景、开放项与观察计划。不要为小项目另建模板、固定字数限制或
额外交接；[小项目上下文示例](../../../../examples/small-project-context.md)只展示这一既有结构的紧凑填写方式，不是新的必填格式。

## 1. 问题发现

先回答：

- 谁遇到什么问题？
- 当前如何处理，成本或风险是什么？
- 期望结果是什么，如何判断改善？
- 哪些内容明确不做？
- 哪些现有行为必须保持？

输出问题陈述、目标用户、成功指标、范围和待澄清项。用户给的是方案时，只有目标仍不明确或现有材料不足以判断时，才追问它试图解决的问题；否则保留已确认的方案约束。

### 尽早处理实质产品选择

在展开详细规格或安排依赖某个选择的工作前，先复用用户请求和可访问已确认来源。只有会改变用户旅程、产品形态、权限/隐私、
关键规则、范围或验收的未决项才需要针对性问题；普通可逆实现细节在既有授权内采用合理默认，不增加确认轮次。产品 Agent 在
产品上下文中区分已核实事实、候选、推荐、开放项和受影响场景。传递问题、由主 Agent 面向用户提问、等待答案与继续独立工作的
规则唯一见[阶段协议的 Early product choices](../stage-agent-protocol.md#early-product-choices)。

用户明确委托指定选择集合时，产品上下文记录委托来源与实际采用项；不能把它写成用户逐项亲自选择。泛化的“继续执行”或“全程推进”
不是未决产品选择的委托。

## 2. 行为设计（BDD）

用具体例子描述外部可见行为：

```gherkin
Given <初始状态>
When <用户或系统动作>
Then <可观察结果>
```

至少覆盖主路径、权限或身份差异、空值/边界、失败与恢复、重复操作和并发影响。复杂规则可使用 Example Mapping：Rule → Example → Question。

场景必须描述业务行为，不嵌入类名、表结构或内部算法。需要稳定引用时使用 `SCN-*` 和 `RULE-*`。

复杂用户旅程、业务分支或状态转换按[图示辅助对齐](software-delivery.md#图示辅助对齐)选择表达，
放在对应用户故事中，与 Given/When/Then 场景共同审阅；产品确认时沿用同一约定，不增加确认步骤。

## 3. 领域澄清

当术语、规则或业务归属复杂时：

1. 建立统一语言，记录同义词和易混概念。
2. 识别实体、值对象、状态变化、业务事件和不变量。
3. 明确每条规则由谁负责、数据事实由谁拥有。
4. 将大领域拆为边界清晰的上下文，并记录它们之间的关系。
5. 用场景验证模型，而不是为了完整性堆叠术语。

可使用 `TERM-*` 标识术语。简单 CRUD 不需要强行建完整领域模型。

## 4. 体验约束

对有界面或人机交互的需求，说明：

- 入口、关键步骤和完成反馈；
- loading、empty、error、offline、permission denied 等状态；
- 响应式、键盘、无障碍和跨端差异；
- 文案与错误信息应帮助用户恢复，而不是只暴露内部错误。

体验决定要能映射回场景和验收条件。

当[包内原型适配](../integrations/product-prototype.md)选择制作候选原型时，在当前产品/规格阶段尽早展示可打开的版本、核心旅程、
实际检查范围、模拟边界和本轮需要判断的选择。围绕具体动作收集反馈，例如请用户完成一次失败后恢复，而不是只问整体是否满意。
将确认、明确委托或开放项的来源写回产品上下文；反馈影响行为时，更新受影响原型版本、场景映射和决定的替代关系，再让工程计划
更新受影响的设计与验证。候选存在、点击检查通过或没有回复都不构成产品确认或生产验证。

## 5. 产品质量

按风险选择质量属性：性能、容量、可靠性、可用性、安全、隐私、合规、可观测、数据质量与模型效果。

每项要求写成可检查的目标，包括适用范围、阈值或样例、测量方式和失败处理。无法量化时说明人工判断标准。可使用 `NFR-*` 和 `EVAL-*`。

## 6. 产品确认

Requirement 进入 ready 前检查：

- 问题、用户、结果和范围明确；
- 关键场景、失败路径和业务规则没有明显矛盾；
- 术语和数据归属足以支持实现；
- 质量与体验要求可验证；
- 依赖和未决问题已处理，或明确不会阻止研发；
- 验收条件能由研发和测试共同理解。

结论写回产品上下文。未满足时保持 captured，并明确下一项需要谁回答。

## 7. 产品决策来源与变更

产品上下文只把当前已确认、会约束产品行为或验收的决定写成绑定要求。对每个需要解释的决定，记录当前决定、它影响的范围或验收条件，以及相关的明确用户确认、对该选择的明确委托或可访问的已确认来源。委托必须同时记录授权语句和实际采用项，且不能伪称为用户亲自选择。不要补写并不存在的旧确认；找不到来源时，把它保留为待确认项，而不是假定已接受。

工程上可在既有授权内自行作出的低风险实现选择，不需要补一次产品确认。假设、推断和仍在比较的替代方案也不自动成为绑定要求，应和当前决定分开写，并说明需要谁在什么条件下确认或排除它们。

当前决定改变时，更新为新决定，并简短说明它取代的决定或来源及其对范围、验收条件或已规划工作的影响。只有仍有效的要求需要在后续设计、Task 和验证中保持覆盖；被明确取代的旧验收条件保留其变更依据，不成为永久必选项。

简单需求可以使用短句和少量条目；只有来源、选择或影响容易混淆时才增加稳定 ID 或元数据。
[PRODUCT.md](../templates/PRODUCT.md) 保留源模板的可审阅结构，不要求批量迁移历史上下文，也不成为第二份进度记录。
